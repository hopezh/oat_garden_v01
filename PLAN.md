# Action Plan — GitHub Pages Static Site for a Growing HTML Collection

A static website that hosts an ever-growing collection of standalone HTML files,
presented as a searchable, filterable, tag-grouped **card grid**. The index page is
built as **React components** (Vite), styled to be interactive, professional, and
minimalistic, with a dark/light theme toggle. New HTML files are indexed automatically
by a Python script and published automatically via GitHub Actions.

---

## Core idea

React + standalone HTML coexist on one static host like this:

- **Vite** builds your React index into `dist/`.
- Your **raw HTML files live in Vite's `public/` folder**, so they are copied into the
  build *untouched* (never bundled).
- A **Python script** generates `posts.json` into that same `public/` folder.
- The React app **fetches `posts.json`** and links each card to its HTML file.

```
push to main  ─▶  GitHub Actions
                    │  run build_index.py   (regenerate public/posts.json)
                    │  npm run build         (Vite → dist/, copies public/ verbatim)
                    │  upload dist/ artifact
                    ▼
                 GitHub Pages  ─▶  https://<username>.github.io/<repo>/
```

---

## Assumptions

- **Project site** at `https://<username>.github.io/<repo>/`, deployed from `main` via
  GitHub Actions. (See *Notes* for the user-site variant.)
- HTML files are **self-contained** (inline CSS/JS or CDN links). If any reference local
  sibling assets, those assets must travel with them.
- **Tags/metadata live inside each HTML file's `<meta>` tags** (the source of truth), so
  `posts.json` is always reproducible.
- Node 20+, Python 3, and Git are installed locally.

## Phase 1 — Scaffold the project locally

```bash
# 1. Create the Vite + React app
npm create vite@latest my-pages -- --template react
cd my-pages

# 2. Install dependencies (Fuse.js powers client-side search)
npm install
npm install fuse.js

# 3. Create the folders for content + the indexer
mkdir -p public/pages          # your standalone HTML files go here
touch build_index.py           # the Python indexer (Phase 2)
```

### Target structure

```
my-pages/
├── .github/workflows/deploy.yml   # CI (Phase 4)
├── public/
│   ├── pages/                     # ← drop your .html files here
│   │   ├── solar-explorer.html
│   │   └── grasshopper-demo.html
│   └── posts.json                 # ← generated by build_index.py
├── src/
│   ├── App.jsx
│   ├── components/
│   │   ├── SearchBar.jsx
│   │   ├── TagFilter.jsx
│   │   ├── PostCard.jsx
│   │   ├── CardGrid.jsx
│   │   └── ThemeToggle.jsx
│   ├── hooks/useTheme.js
│   ├── theme.css                  # CSS variables (light/dark tokens)
│   └── main.jsx
├── build_index.py
├── vite.config.js
└── package.json
```

### Set the base path

In `vite.config.js`, so assets resolve under the repo subpath:

```js
import { defineConfig } from 'vite'
import react from '@vitejs/plugin-react'

export default defineConfig({
  plugins: [react()],
  base: '/my-pages/',   // ← project site: '/<repo-name>/'
                        //   user site (username.github.io): use '/'
})
```

### Component responsibilities

- **`App.jsx`** — fetches `posts.json`; holds search text, selected tags, and theme;
  runs Fuse.js; passes filtered results down. Fetch and links must respect the base path:
  - `fetch(`${import.meta.env.BASE_URL}posts.json`)`
  - `href={`${import.meta.env.BASE_URL}pages/${post.file}`}`
- **`SearchBar`** — Fuse.js fuzzy search over title / description / tags.
- **`TagFilter`** — derives the unique tag set from posts; renders clickable chips with
  multi-select; a "group by tag" toggle switches the grid into tag-grouped sections.
- **`PostCard`** — title, description, date, tag chips; the whole card links to the HTML
  file (use `target="_blank"` for a new tab).
- **`CardGrid`** — responsive CSS-grid of cards.
- **`ThemeToggle` + `useTheme`** — flips `data-theme` on `<html>`; `theme.css` holds the
  light/dark CSS variables. Reuse the **Fraunces + teal** tokens from the design guide so
  the index and the hosted pages feel like one coherent site.

Run locally with `npm run dev` (after Phase 2 has produced a `posts.json`).

## Phase 2 — Python script to auto-index the HTML files

`build_index.py` scans `public/pages/`, parses each file's `<title>` and `<meta>` tags,
and writes `public/posts.json`. Because tags live in the files, the JSON is fully
reproducible; an optional merge step preserves any manual edits.

**What it does, step by step:**

1. Glob every `*.html` in `public/pages/`.
2. For each file, parse the HTML (stdlib `html.parser`, or `beautifulsoup4` if preferred)
   and extract `title` (from `<title>`), plus `description`, `keywords`→`tags`, and
   `date` (from `<meta name="...">`).
3. Fall back gracefully: no title → use the filename; no date → use the file's
   modification time.
4. Build records: `{ "file", "title", "description", "tags": [...], "date" }`.
5. *(Optional)* Merge with the existing `public/posts.json` so hand-curated fields survive.
6. Sort by date (newest first) and write `public/posts.json`.

**Expected `<head>` metadata in each HTML file:**

```html
<title>Interactive Solar Irradiance Explorer</title>
<meta name="description" content="A three.js scene visualizing annual irradiance.">
<meta name="keywords" content="threejs, dataviz, solar">
<meta name="date" content="2026-05-01">
```

**Run it whenever you add files:**

```bash
python build_index.py
```

For convenience, wire it into npm so dev/build always re-index first — add to
`package.json` scripts (use `python3` on macOS/Linux if needed):

```json
{
  "scripts": {
    "predev": "python build_index.py",
    "prebuild": "python build_index.py"
  }
}
```

## Phase 3 — `git init` and sync with an empty GitHub repo

**Locally:**

```bash
# from inside my-pages/
git init
printf "node_modules\ndist\n.DS_Store\n" > .gitignore
git add .
git commit -m "Initial commit: Vite + React index, indexer, sample pages"
```

> Committing `public/posts.json` is fine and lets `npm run dev` work without re-running
> Python first; CI regenerates it fresh on every deploy regardless.

**On GitHub:** create a new repository named `my-pages` — **empty**, with *no* README,
.gitignore, or license (so histories don't conflict). Copy the repo URL.

**Connect and push:**

```bash
git remote add origin https://github.com/<username>/my-pages.git
git branch -M main
git push -u origin main
```

## Phase 4 — GitHub Actions to build and deploy automatically

Uses GitHub's **official Pages deployment flow** (the current recommended approach): it
builds from `main` and deploys the artifact directly — no `gh-pages` branch, no
`.nojekyll` file, and no personal access token required.

**First**, in the repo: **Settings → Pages → Build and deployment → Source → "GitHub Actions"**.

**Then** create `.github/workflows/deploy.yml`:

```yaml
name: Build and deploy site
on:
  push:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read
  pages: write
  id-token: write

concurrency:
  group: pages
  cancel-in-progress: true

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-python@v5
        with:
          python-version: '3.12'

      - name: Regenerate posts.json from /public/pages
        run: python build_index.py

      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm

      - run: npm ci
      - run: npm run build          # Vite → dist/ (includes public/ verbatim)

      - uses: actions/configure-pages@v5
      - uses: actions/upload-pages-artifact@v3
        with:
          path: ./dist

  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    steps:
      - id: deployment
        uses: actions/deploy-pages@v4
```

Commit and push it. Watch the run under the **Actions** tab; when it finishes, the site is
live at `https://<username>.github.io/my-pages/`.

## Phase 5 — The ongoing workflow (daily loop)

Adding a page is three steps:

```bash
# 1. Drop the new file in (make sure it has <title> and <meta> tags)
cp ~/Downloads/new-thing.html public/pages/

# 2. (Optional) preview locally — predev re-indexes automatically
npm run dev

# 3. Publish
git add public/pages/new-thing.html public/posts.json
git commit -m "Add: new-thing"
git push
```

The push triggers the workflow: CI re-runs `build_index.py` (regenerating `posts.json`
from whatever is in `public/pages/`), rebuilds the React app, and redeploys. The new card
appears on the live site within a minute or two — no manual index editing ever.

## Notes and gotchas

- **User site vs project site** is the one fork: a user site (`username.github.io`) sets
  `base: '/'` in `vite.config.js`; everything else is identical. Using
  `import.meta.env.BASE_URL` for all fetches/links means the React code itself never
  changes between the two.
- **Self-contained HTML matters.** Pages with inline or CDN-loaded assets work from any
  path. Pages with relative local asset references need those assets placed alongside them
  in `public/pages/`.
- **First deploy is blank?** Almost always a wrong `base` value — it must exactly match
  `/repo-name/`, including both slashes.
- **Theme persistence:** in a real deployed app you *can* use `localStorage` to remember
  the user's theme choice across visits (that limitation only applies inside chat-preview
  sandboxes, not on GitHub Pages).
