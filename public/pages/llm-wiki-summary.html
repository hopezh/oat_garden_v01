The LLM Wiki Pattern

A persistent, LLM-maintained knowledge base that compiles knowledge once and keeps it current — instead of rediscovering it from scratch on every query.

Source gist.github.com/karpathy Format markdown · git repo Contrast RAG retrieval
01 — The premise

The core idea

The post is explicitly an "idea file": abstract by design, meant to be pasted into a coding agent (Claude Code, Codex, OpenCode) so the agent builds a concrete version in collaboration with you. Its job is to communicate the pattern, not a specific implementation.

The shift away from RAG

Most people's experience of LLMs + documents is RAG: upload files, the model retrieves relevant chunks at query time, and generates an answer. It works — but the LLM rediscovers knowledge from scratch on every question. Nothing accumulates. The alternative reframes where the work happens:

RAG re-derives an answer from raw chunks each time; the LLM Wiki compiles knowledge into a persistent layer that is read and reused.

Instead of retrieving from raw documents at query time, the LLM incrementally builds and maintains a persistent wiki — a structured, interlinked set of markdown files that sits between you and the raw sources. Adding a source isn't just indexing it: the LLM reads it, extracts the key information, and integrates it — updating entity pages, revising summaries, flagging where new data contradicts old claims. The wiki is a compounding artifact: cross-references are already there, contradictions already flagged, synthesis already current.

The mental model

"Obsidian is the IDE; the LLM is the programmer; the wiki is the codebase."

You own sourcing, exploration, and asking the right questions. The LLM does all the grunt work — summarizing, cross-referencing, filing, and bookkeeping. You rarely write the wiki yourself; you browse it in real time as the model edits.

Where it applies

Personal

Goals, health, psychology — filing journal entries and notes into a structured picture of yourself over time.

Research

Going deep over weeks — reading papers and reports, building a comprehensive wiki with an evolving thesis.

Reading a book

File each chapter; build pages for characters, themes, plot threads — a personal fan-wiki as you read.

Business / team

An internal wiki fed by Slack threads, transcripts, and project docs — kept current because the LLM does the upkeep.

Also: competitive analysis, due diligence, trip planning, course notes, hobby deep-dives — anything where knowledge accumulates and you want it organized rather than scattered.

02 — Structure

Architecture: three layers

The system is deliberately simple — three layers with a strict ownership boundary between what you control and what the LLM controls.

Raw sources flow up through the schema's rules into the LLM-owned wiki. The schema governs how the LLM behaves.

① Raw sources — YOU OWN · IMMUTABLE

Your curated collection of source documents: articles, papers, images, data files. The LLM reads from them but never modifies them. This is your source of truth.

② The wiki — LLM OWNS ENTIRELY

A directory of LLM-generated markdown: summaries, entity pages, concept pages, comparisons, an overview, a synthesis. The LLM creates pages, updates them as new sources arrive, maintains cross-references, and keeps everything consistent. You read it; the LLM writes it.

③ The schema — CO-EVOLVED

A config document (CLAUDE.md for Claude Code, AGENTS.md for Codex) defining structure, conventions, and workflows for ingesting, answering, and maintaining. This is the key file — it turns the LLM into a disciplined wiki maintainer rather than a generic chatbot. You and the LLM refine it over time for your domain.

03 — The loop

Three operations

Day-to-day, the wiki runs on three repeatable operations. The first two feed the wiki; the third keeps it healthy.

Ingest

Drop a source in and tell the LLM to process it. It reads, discusses takeaways with you, writes a summary page, updates the index, revises relevant entity and concept pages, and appends to the log. A single source might touch 10–15 pages. Ingest one at a time and stay involved, or batch with less supervision.

Query

Ask questions against the wiki. The LLM finds relevant pages, reads them, and synthesizes a cited answer — as a page, comparison table, slide deck (Marp), or chart. The key insight: good answers get filed back into the wiki as new pages, so your explorations compound just like ingested sources, instead of vanishing into chat history.

Lint

Periodically health-check the wiki. Look for contradictions between pages, stale claims superseded by newer sources, orphan pages with no inbound links, concepts mentioned but lacking their own page, missing cross-references, and data gaps a web search could fill. Keeps the wiki healthy as it grows.

04 — Navigation

Two special files: index & log

As the wiki grows, two files help both you and the LLM navigate it. They serve different purposes — one spatial, one temporal.

index.md is the content catalog read first on every query; log.md is the append-only timeline.

index.md — content-oriented

A catalog of everything in the wiki: each page with a link, a one-line summary, and optional metadata, organized by category. Updated on every ingest. When answering a query, the LLM reads the index first to find relevant pages, then drills in. Karpathy notes this works surprisingly well at moderate scale (~100 sources, hundreds of pages) and avoids the need for embedding-based RAG infrastructure.

log.md — chronological

An append-only record of what happened and when — ingests, queries, lint passes. With a consistent prefix per entry, it becomes parseable with plain unix tools:

grep "^## \[" log.md | tail -5 → the last five entries, no tooling required

Optional tooling & tips

  • CLI search — at scale, add a local markdown search engine (e.g. qmd: hybrid BM25 + vector, on-device, with CLI and MCP server). At small scale the index file is enough.
  • Obsidian Web Clipper converts web articles to markdown for quick capture; local image download lets the LLM reference images directly.
  • Graph view shows the shape of the wiki — hubs vs. orphans. Marp generates slide decks from wiki content. Dataview runs queries over YAML frontmatter.
  • It's just a git repo of markdown — so version history, branching, and collaboration come for free.
05 — The payoff

Why this works

The tedious part of a knowledge base isn't the reading or the thinking — it's the bookkeeping. Updating cross-references, keeping summaries current, noting contradictions, maintaining consistency across dozens of pages.

Humans abandon wikis because the maintenance burden grows faster than the value. LLMs don't get bored, don't forget a cross-reference, and can touch 15 files in one pass. The wiki stays maintained because the cost of maintenance approaches zero.

Maintenance burden vs. value as the wiki grows

The division of labor. The human's job: curate sources, direct the analysis, ask good questions, and think about what it all means. The LLM's job: everything else.

The Memex connection

The idea echoes Vannevar Bush's Memex (1945) — a private, curated knowledge store with associative trails between documents, where the connections matter as much as the documents themselves. Bush's vision was closer to this than to what the web became. The part he couldn't solve was who does the maintenance. The LLM handles that.

A note on scope

The document is intentionally abstract — it describes the pattern, not an implementation. Directory structure, schema conventions, page formats, and tooling all depend on your domain and your LLM. Everything is optional and modular: pick what's useful, ignore what isn't, and instantiate a version that fits your needs.
