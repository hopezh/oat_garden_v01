Static-Site Playbook

Host a growing collection of standalone HTML as one searchable site.

Your generated pages already render on their own. The only missing piece is a front door — a single index that knows what exists and lets you browse, search, filter, and group it. Here's the whole design, end to end.

00 — Overview

The big idea

This is simpler than it first looks, because each of your HTML files is already self-contained and renders independently in a browser. You don't convert or rebuild them. You add exactly two new pieces on top: a manifest that lists what you have, and one index page that reads it. Clicking an entry just navigates the browser to that file — rich contents and all.

01 — Architecture

Three layers in one repo

A

Your HTML files /posts/

Dropped into a folder. They already render, so a click simply opens them in a new page. No build step ever touches them.

B

A manifest posts.json

One JSON file listing each post's title, date, tags, description, and path. This is what makes search, filtering, and grouping possible without any server.

C

One home index.html

Fetches posts.json, renders the cards or list, and runs search & filter entirely in the browser.

How it gets served

A static host serves these files verbatim — it takes your HTML, CSS, and JavaScript straight from the repository and publishes them, with no server-side processing. Every interactive thing happens client-side, which is exactly what static hosting is best at.

02 — Keeping it current

Make each file self-describing

The "ever-growing" requirement is the real design question. The trick is to let each file carry its own metadata in <meta> tags, so it describes itself:

posts/solar-explorer.html — <head>
<title>Interactive Solar Irradiance Explorer</title>
<meta name="description" content="A three.js scene visualizing annual irradiance.">
<meta name="keywords" content="threejs, dataviz, solar">
<meta name="date" content="2026-05-01">

Title comes from <title>; tags, description, and date from the meta tags. Just ask Claude to include these when it generates a page, and your files arrive ready to index.

A small Python build script

A script scans /posts/, reads each file's metadata, and writes posts.json. The key trick: merge with the existing manifest rather than overwrite it — so hand-curated tags on old posts are preserved while new files get auto-added.

Your whole workflow becomes: drop a file in the folder → run the script → commit. That's it.

Automate it with GitHub Actions

A workflow runs the script on every push, regenerates posts.json, and commits it back. After that you never touch the manifest by hand — push a new HTML file and the index updates itself.

03 — Search, filter & tags

Do it all client-side

For a personal collection (tens to low hundreds of files), everything runs in the browser. Tags become clickable filter chips, keyword search runs over title / description / tags, and group-by-tag is just a groupBy over the same JSON.

# threejs# dataviz# solar# pytorch# grasshopper# radiance

Fuse.js vs Pagefind

★ Recommended

Fuse.js / MiniSearch + posts.json

No backend, full control of the card UI, fuzzy search. The only cost is generating an index file — which your Python script already does. Loads the whole dataset client-side, so it can slow down only once you're well into the thousands.

Upgrade path

Pagefind

Crawls your built HTML and indexes the full text inside each page. Reach for it when you want to search content within documents, not just their metadata.

04 — Where to host

GitHub Pages

The most frictionless choice if your files are already heading into a Git repo, and free for public repos. A user site needs a repo named exactly username.github.io; a project site gives you username.github.io/reponame.

The .nojekyll gotcha

Add an empty .nojekyll file at the repo root. By default, Pages runs files through Jekyll, which ignores underscore-prefixed files and can interfere with arbitrary HTML. This empty file disables that and serves your files untouched.

Solid alternatives

Cloudflare Pages and Netlify both have generous free tiers, easy Git integration, custom domains, and fewer build quirks. Vercel is aimed at Next.js apps — overkill here, unless you later rebuild the index as a Next.js / React app, which is a natural future iteration given you're learning Next.js.

05 — Suggested first version

Repo layout

my-pages/
my-pages/
├── .nojekyll            # disable Jekyll processing
├── index.html           # browse / search / filter UI
├── posts.json           # generated manifest
├── build_index.py       # scans /posts, rebuilds manifest
├── posts/               # your HTML files live here
└── .github/workflows/   # optional: auto-run on push

First steps

Get the manual version workingWrite build_index.py and a card-based index.html with Fuse.js search and tag filtering.
Confirm the feelMake sure browsing, search, and filtering behave the way you want before adding moving parts.
Automate the manifestAdd the GitHub Action so the index updates itself on every push.
(Later) Level upSwap the index page for a React / Next.js app, or add Pagefind for full-text search inside documents.

Want this turned into real files? The next step is scaffolding build_index.py (with tag-preserving merge), a polished card-based index.html, and the GitHub Actions workflow — as plain HTML/JS or as a React component.
