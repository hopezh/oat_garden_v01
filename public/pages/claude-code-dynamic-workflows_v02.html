Claude Code Dynamic Workflows, explained

Claude writes a JavaScript orchestration script on the fly, a runtime fans it out across tens to hundreds of parallel subagents in the background, and you get back a single, verified answer instead of a turn-by-turn transcript.

01 — Basic concepts

What a dynamic workflow actually is

A dynamic workflow is a JavaScript orchestration script that Claude writes from your plain-language request. A separate runtime executes that script in the background while your chat session stays free to keep working. The script — not the conversation — holds the loops, the branching, and the intermediate state.

Where a normal session works through a problem turn by turn, a workflow fans the work out across many subagents running in parallel, checks the results before folding them in, and returns one coordinated answer. Independent agents attack the problem from different angles, other agents try to refute their findings, and the run keeps iterating until the answers converge.

How a run works

Plan

Claude reads your prompt and writes a script that breaks the job into subtasks.

Fan out

The runtime spawns subagents in parallel; intermediate results live in script variables, not Claude's context.

Verify

Findings are independently re-checked / adversarially reviewed before they count.

Converge & report

The run iterates until results stabilise, then returns one cited, coordinated answer.

Two ways to trigger one

  • Put the word workflow anywhere in a prompt — Claude Code highlights it and writes a script for that one task. (You decide to fan out.)
  • Run /effort ultracode — combines xhigh reasoning effort with automatic orchestration, so Claude itself decides when each task warrants a workflow for the whole session. (Claude decides.)

There's also a bundled workflow, /deep-research, and once a run does what you wanted you can press s in /workflows to save its script as your own reusable /command.

Availability & hard limits

  • Research preview on all paid plans (on by default for Max/Team and the API; Enterprise admin-gated), plus Bedrock, Vertex AI, and Microsoft Foundry.
  • Up to 16 concurrent agents locally, 1,000 agents total per run (a guard against runaway loops).
  • No mid-run user input — only permission prompts can pause a run. Runs are resumable, but only within the same session.
02 — The key difference

vs. the conventional “orchestrator + subagents”

Subagents, skills, and workflows can all run a multi-step task. The decisive difference is one thing: who holds the plan.

With ordinary subagents and skills, Claude is the orchestrator. It decides turn by turn what to spawn next, and every intermediate result lands back in its context window. That works well for a handful of delegated tasks — but the context fills up as the job grows, and an interruption restarts the whole turn.

A dynamic workflow moves the plan into code. The script owns the loop, the branching, and the intermediate results, so Claude's context only ever holds the final answer. That single shift is what lets a run scale to hundreds of agents, stay on track no matter how big the task gets, and be saved and re-run exactly.

03 — Fit

The most suitable scenarios

Reach for a workflow when a task needs more agents than one conversation can coordinate, or when you want the orchestration codified as a script you can read and re-run.

Where it shines

  • Codebase-wide audits — bug hunts, security/auth sweeps, input-validation and unsafe-pattern passes, profiler-guided optimisation. Parallel search, then independent verification of every finding so the report surfaces real issues.
  • Large migrations & modernisation — framework swaps, API deprecations, language ports spanning hundreds to thousands of files, end-to-end.
  • High-stakes work you need checked twice — independent attempts at the same problem plus adversarial agents trying to break the result before you see it.
  • Cross-checked research — many sources fetched in parallel and weighed against each other, with claims that fail verification filtered out.
  • Stress-testing a plan — drafting it from several independent angles before you commit to one.

Where it's the wrong tool

  • Quick, routine, or exploratory tasks — the token cost and setup outweigh the benefit.
  • Anything needing human sign-off mid-run; there's no mid-run input, so split staged approvals into separate workflows.
  • Cost-sensitive contexts where an order-of-magnitude token jump isn't acceptable.
04 — Trade-offs

Pros & cons

PROS What you gain

  • Scale: tens–hundreds (up to 1,000) of agents coordinated in one session.
  • Clean context: plan & state live in the script, so big tasks don't bloat the conversation.
  • Built-in verification: adversarial review yields results a single pass can't reach.
  • Long-running & resumable: progress is saved; an interrupted run picks up where it left off.
  • Repeatable: save the script as a /command and re-run the exact orchestration.
  • Background: the session stays responsive while agents work.

CONS What it costs

  • Token usage: meaningfully higher — a large run can shift the bill by an order of magnitude.
  • Research preview: still maturing; behaviour may change.
  • No mid-run input: only permission prompts pause it; staged sign-off needs separate runs.
  • Resume is session-bound: exit Claude Code and the run starts fresh.
  • Auto-approved edits: spawned agents run in acceptEdits mode — manage your tool allowlist.
  • Model cost: every agent uses your session model unless the script routes a stage elsewhere.

Cost tip: check /model before a big run and ask Claude to route mechanical stages to a smaller model. Start on a scoped task to feel out usage.

05 — In practice

Two worked examples

Example 1 — Codebase-wide auth/security audit

A discovery + verification pattern: too many files for one context, and you want every finding double-checked before it reaches you.

claude code — cli
> Run a workflow to audit every API endpoint under
  src/routes/ for missing auth checks, then verify
  each finding before reporting.

Scan in parallel

Agents each take a slice of src/routes/, flagging missing or weak auth, input-validation gaps and unsafe patterns. Candidates accumulate in script variables.

Independent verification

A fresh agent adversarially re-checks each candidate; false positives are filtered out so only real issues survive.

Single report

You come back to one report of confirmed issues with file locations — not a noisy turn-by-turn transcript.

Save & re-run

Open /workflows, press s, and save it as /auth-audit to run the same sweep on every branch.

Example 2 — Migrate a data pipeline from pandas to polars

A large migration across many modules — the same shape Anthropic showcased with the 750k-line Bun port (Zig→Rust), scaled to a data-engineering codebase. Keep behaviour identical and the test suite green.

claude code — cli
> /effort ultracode
# then:
> Create a workflow to migrate every module under
  src/pipeline/ from pandas to polars, keeping behaviour
  identical and pytest green. Use a smaller model for the
  mechanical port stages.

Map

Agents catalogue the pandas APIs each module uses and their polars equivalents, flagging tricky spots (index semantics, dtypes, apply vs expressions).

Port in parallel

Many agents each rewrite one module as a behaviour-identical polars version, with reviewer agents per file checking correctness.

Fix loop

The run drives the build and pytest until both pass clean, agents iterating on failures until results converge.

Optimise (optional)

An overnight pass tackles unnecessary copies / eager frames and opens a PR per change for your final review.

Watch either run live with /workflows — each phase shows its agent count, token total and elapsed time, and you can drill into any single agent's prompt and result.
