Building the LLM Wiki

From Karpathy's abstract pattern to a running system: where it actually pays off, which software to choose, and exactly how to wire the agent, editor and search into one compounding knowledge base.

Pattern karpathy / llm-wiki.md Core stack agent · markdown · git Scope scenarios + architecture

Karpathy's gist is deliberately an idea file — it describes a pattern, not an implementation, and tells you to hand it to a coding agent and instantiate your own version.1 This research fills that gap: it answers the two questions the gist leaves open — when is the pattern the right tool, and what do you actually install and connect — drawing on the original post and the working implementations that have since appeared in its comment thread and on GitHub.2

01 — Choosing the problem

Where the LLM Wiki pays off

The wiki earns its keep on bodies of knowledge that accumulate over time and that you'll query repeatedly — where the value comes from synthesis across sources, not from any single document. It is the wrong tool for one-off lookups, for corpora that never change, or for collections so large they can't be reasoned over as a whole.

The real decision: context vs. RAG vs. wiki

A recurring theme in practitioners' reports is that the choice between an LLM Wiki and classic RAG is fundamentally a question of corpus magnitude.4 Below roughly 50k–100k tokens (about 150–200 dense pages), keeping structured markdown in context wins decisively: near-perfect retrieval, almost no infrastructure, and global reasoning over the whole corpus. RAG only becomes necessary when the corpus can't fit at all; in between sits a hybrid.4

Corpus size → recommended approach

The LLM Wiki occupies the band where a corpus is too valuable to re-derive every query, but small enough to reason over whole. Most personal and team knowledge lives here.

Rule of thumb

If your wiki's index plus the handful of pages a query touches comfortably fits the model's context window, you do not need embeddings, a vector database, or a chunking pipeline. An index.md that lets the agent open fewer whole files is an optimisation, not a retrieval system — and it stays reliable in a way chunked RAG does not.14

Fit by use case

The pattern generalises across domains. The strongest fits share three traits: sources arrive incrementally, answers require connecting multiple sources, and the same knowledge gets reused.

Strong fit

Research deep-dives

Reading papers and reports over weeks, building a wiki with an evolving thesis. The canonical use case.1

Strong fit

Team / internal wiki

Fed by Slack, transcripts and project docs; stays current because the agent does the upkeep no one wants to.1

Good fit

Personal / continuity

Goals, health, journals — a structured, queryable picture of yourself that any model can load to stay in phase.

Good fit

Diligence & analysis

Competitive analysis, due diligence, course notes — anywhere knowledge would otherwise scatter across tools.

Caution

Subjective domains

In the humanities, contradiction is content, not a defect — tune lint to preserve tension rather than reconcile it.13

Poor fit

Static or huge corpora

One-off lookups, frozen archives, or millions of tokens — re-derivation or RAG beats the maintenance overhead.

A concrete instantiation: a building-science research wiki

As a worked example of the strongest scenario, picture a multi-week research effort across daylighting and solar-energy papers, simulation reports, and your own Radiance result sets. Each ingested paper becomes a concept page (e.g. spatial-daylight-autonomy, annual-irradiance) cross-linked to method pages (Radiance workflows, PyTorch surrogate models) and source summaries. A query like "which papers contradict the assumed sky model?" is answered from the compiled wiki and filed back as its own page — so the synthesis compounds instead of evaporating into chat history. The same shape works for an ML/DL literature wiki tracing a lineage of architectures, with each paper's claims preserved and back-linked.

02 — Components

The stack: which software

The minimum viable system is remarkably small: an agent, a folder of markdown, and git.15 Everything else is modular and added only when a real need appears. The components fall into five roles.

Five roles, from the immutable source layer at the base to the agent that owns the wiki at the top. Only the agent, markdown and git are required; the rest are optional add-ons.

The agent & the schema — REQUIRED

A coding agent that can read and write files in a directory is the engine. The gist names Claude Code, OpenAI Codex and OpenCode / Pi.1 The agent's behaviour is governed by a single schema file at the repo root — CLAUDE.md for Claude Code, AGENTS.md for Codex. This file is the heart of the system: it defines the directory structure, the page formats, the ingest / query / lint workflows, and the hard rules (never fabricate a figure; treat sources as untrusted). It is what turns a generic chatbot into a disciplined wiki maintainer, and you co-evolve it with the agent over time.1

The editor / front-end — RECOMMENDED

Because the wiki is plain markdown, any editor works — including Neovim or VS Code. Obsidian is the common recommendation because it adds a live graph view (the fastest way to see hubs vs. orphan pages), [[wiki-links]], and a plugin ecosystem. The intended workflow is the agent on one side making edits and Obsidian on the other, browsing the results in real time. Useful Obsidian add-ons: Web Clipper (converts web articles to markdown sources), Dataview (dynamic tables over YAML frontmatter), and Marp (slide decks from wiki pages).1 For block-level safety against concurrent edits, some practitioners prefer Logseq, whose outliner stores each block with a UUID.14

Search — OPTIONAL, ADD AT SCALE

At small scale index.md is enough — the agent reads it first, then opens the relevant pages. As the wiki grows you want real search. qmd (by Tobi Lütke) is the tool the gist points to:1 an on-device markdown search engine combining BM25 full-text, vector similarity and LLM re-ranking, all local via SQLite (FTS5 + sqlite-vec) and node-llama-cpp with GGUF models.3 Crucially it exposes both a CLI (the agent shells out to it) and an MCP server (the agent calls it as a native tool) — the two ways the search layer connects to the agent.3 You can also vibe-code a naive grep-based search script if that is all you need.

Ingest extractors — OPTIONAL, BY SOURCE TYPE

If your sources are text-only you need none of this. The moment you add PDFs, office docs or media, you reach for Python: PyMuPDF for PDF text and images, python-docx for Office files, Whisper for audio/video transcripts, and Instructor or Pydantic-AI for structured LLM extraction. A practical lesson from people who scaled the pattern: these extractors stay as Python satellites the agent calls as subprocesses or MCP tools — don't try to fold them into the agent itself.10

Storage & output — RECOMMENDED

The whole wiki is a git repo of markdown, so version history, branching and team collaboration come for free — and provenance becomes recoverable (a poisoned or wrong entry is findable and revertible).19 On the output side, the agent can render answers as Marp slide decks or as charts (matplotlib, or Plotly for a Python-first user). An optional llms.txt export feeds the wiki into downstream LLM workflows.8

03 — Connections

Wiring it together

The components connect through three simple mechanisms: a shared folder on disk, the schema file as the control plane, and MCP or CLI as the way tools attach to the agent. There is no server, no database, and no API to stand up for the base system.

Directory layout

A single repository holds everything. The boundary between what you own and what the agent owns is enforced by convention in the schema, not by tooling:

my-wiki/
├─ CLAUDE.md # schema — the control plane
├─ raw/ # your sources · immutable · agent reads only
│  └─ assets/ # locally-downloaded images
├─ wiki/ # agent-owned markdown pages
│  ├─ entities/ concepts/ sources/
│  ├─ index.md # content catalog · read first on query
│  └─ log.md # append-only timeline
└─ tools/ # optional extractors / search scripts

Data flow & protocols

The diagram below shows how the parts talk. You curate sources into raw/ (often via Obsidian Web Clipper). The agent reads the schema, reads index.md, then reads sources and writes pages into wiki/. Search and extractors attach as MCP tools or are invoked over the CLI. Git versions the whole thing; Obsidian renders it for you to browse.

Solid lines: file reads/writes. Dashed: tool calls over MCP or CLI. The schema governs every agent action; git wraps the entire repo.

  • Agent ⇄ files. The only hard requirement — the agent reads raw/ and the schema, and reads/writes wiki/. Everything else is optional.
  • Agent ⇄ search. Register qmd as an MCP server so the agent searches as a native tool, or let it shell out to the qmd CLI. Use the index file alone until search is genuinely needed.
  • Agent ⇄ extractors. Python extractors run as subprocesses or MCP tools, returning clean text/JSON the agent files into the wiki.
  • Human ⇄ wiki. Obsidian (or your editor) points at the same folder for graph view and reading; Web Clipper feeds raw/.

Optional: a two-model split

As cost and latency matter, several implementations adopt per-role providers: a small, fast model (local via Ollama or LM Studio) does cheap extraction and concept-spotting, while a heavier model (cloud or large local) writes the cross-linked articles.710 The schema assigns each operation to a model; the rest of the architecture is unchanged.

04 — The loop

The operating loop

Once wired, the system runs on three repeatable operations. The first two feed the wiki; the third keeps it healthy. The compounding effect comes from one habit: good answers are filed back as pages.

Ingest and query both write into the wiki; lint repairs it. Every pass leaves the knowledge base richer than it found it.

Ingest

Drop a source in raw/ and ask the agent to process it: it reads, discusses takeaways, writes a summary page, updates the index, revises related entity/concept pages, and appends to the log. A single source may touch 10–15 pages.1 Ingest one at a time while you're learning the workflow; batch later.

Query

Ask against the wiki. The agent reads the index, opens the relevant pages, and synthesises a cited answer — page, comparison table, slide deck or chart. The key move: file good answers back into the wiki so explorations compound like ingested sources.1

Lint

Periodically health-check: contradictions, stale claims superseded by newer sources, orphan pages, concepts lacking a page, missing cross-references, and data gaps to fill with a search. At scale, run lint in small batches over a randomised source order so cross-cutting contradictions surface rather than biasing toward what you ingested first.11

05 — Holding up

Scaling & hardening

The base pattern is robust at the scale most people use it — roughly a hundred sources and a few hundred pages. Push past that and predictable problems appear. The implementations that have matured around the gist converge on a small set of fixes.

As a wiki grows, four pressures emerge; each has a known mitigation drawn from production implementations.

Pressure at scaleWhat goes wrongMitigation
Concurrent writesTwo agents ingesting at once corrupt a page mid-write.Per-file locking; or a block-AST store (Logseq) with per-block UUIDs.514
Retrieval driftThe index stops surfacing the right pages on a large vault.Hybrid retrieval — contextual prefix + BM25 + re-rank (qmd / contextual-retrieval).5
Edge explosionDense cross-links overwhelm the model around ~1,000 files.Keep links sparse and typed; don't densify edges Wikipedia-style by hand.12
Prompt injectionA crafted source plants instructions that poison later sessions.Nonce-delimit untrusted sources, second-model review, trust-tier by host, git provenance.9
Ingestion-order biasThe synthesis tilts toward sources read first.Randomised, batched lint with a persistent scratchpad across sessions.11
Stale claimsPages silently outlive the sources they summarised.Page lifecycle (draft → active → stale → contradicted → archived) keyed on source hashes.8
A note on hallucination

The sharpest critique of the pattern is that LLM-only maintenance can compound errors.12 The durable defences are provenance (every claim traces to a source line, so a wrong entry is findable and revertible through git) and a hard schema rule against inventing figures — leave a placeholder rather than guess.9 Keep yourself in the loop on emphasis; let the agent do the bookkeeping.

Don't start from zero: turnkey implementations

Because the gist went viral, a field of open-source implementations now exists. Rather than build the schema and tooling from scratch, you can fork one and adapt it. A representative sample:

  • claude-obsidian (MIT) — the three layers as a daily driver in Claude Code + Obsidian, with auto-generated graph, per-file locking and optional hybrid retrieval.5
  • Funes — a turnkey version where everything, including outputs, lives in one git repo, with a browsable example library.6
  • Synto — local-first, designed around Ollama / LM Studio with per-role providers; plain markdown, Obsidian-friendly, no vector DB required.7
  • Synthadoc — adds a five-state page lifecycle and one-command export to llms.txt, GraphML and provenance-rich JSON.8
  • secure-llm-wiki — hardens the pattern against prompt injection with nonce-delimiting, four-eyes review and a threat model.9

Karpathy's own advice still applies: share the gist with your agent and instantiate a version that fits your domain. Start small, ingest one source at a time, and let the wiki compound from the first.
