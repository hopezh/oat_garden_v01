Overview

The memory problem this kit solves

“Combing through” a codebase with Claude Code in one session does not persist. Each session begins with a fresh context window1 — unless the understanding is written into files that load at startup.

Two mechanisms carry knowledge across sessions: CLAUDE.md files, which you write and control, and auto memory, notes Claude writes for itself based on your corrections1. Auto memory is convenient but uncurated — what it saves doesn’t always match what you’d want2. This kit therefore treats the curated CLAUDE.md as the source of truth and auto memory as a supplement.

CLAUDE.md — you write it

Loaded every session. Deliberate, versioned, reviewable. Adherence drops as it grows, so it must stay lean2.

Auto memory — Claude writes it

Background notes under ~/.claude/projects/<project>/memory/, loaded at startup2. Helpful, but not a substitute for curation.

The Kit

One router, four knowledge files

The kit is tuned for a multi-page web app built with Next.js (App Router) + three.js + @react-three/fiber + @react-three/drei, in plain JavaScript, managed with Bun4.

The line budget

Reported practice puts the adherence ceiling for an always-loaded CLAUDE.md at roughly 200 lines2. The kit keeps the root file at about half that and pushes depth into docs/, which is only read when the routing table says it’s relevant.

File by File

What each file holds, and why

CLAUDE.mdroot · always loaded

A router, not an encyclopedia. It holds only what must apply in every session: project identity (JS-only, Bun-only), the command block (bun dev, bun run build…), the repo layout, and eight hard rules. A table then tells Claude when to read each docs file — e.g. “touching canvas code → read R3F-PATTERNS.md”.

The eight hard rules encode the classic Next.js + R3F failure modes: 'use client' boundaries, mounting <Canvas> via dynamic(ssr:false), no per-frame allocation, no setState in useFrame, disposal of manually created resources, drei loaders with preload, ESM-only, and ask-before-adding dependencies.

docs/ARCHITECTURE.mdread when touching structure

The system theory. An ASCII diagram of the whole app, then: how routing works (server-component pages, client-only canvas), the single shared Scene.jsx wrapper that owns the only <Canvas>, the zustand store as the DOM ⇄ canvas bridge, the asset pipeline table (draco glb / ktx2 / hdr), and the performance model. Each subsection includes the why, so a future session doesn’t “fix” a deliberate choice.

docs/CONVENTIONS.mdread when writing new files

How code should look. Naming tables (components, hooks, helpers, assets), component file structure, JavaScript style with JSDoc instead of TypeScript, state rules (zustand for shared, never three.js objects in state), the asset optimization commands run with bunx (gltf-transform, gltfjsx), asset size budgets, and git conventions — including that bun.lock is the only lockfile allowed.

docs/R3F-PATTERNS.mdread for any canvas code

✅/❌ pattern pairs for the render loop (scratch objects, transient store reads, fps-independent damping vs. per-frame allocation and setState), loading via drei with Suspense, pointer-event hygiene, color-space rules for textures, a ranked performance toolkit (Instances → demand frameloop → LOD → adaptive dpr), camera/controls conventions, Next.js-specific boundaries, and a symptom → suspects debugging table (black screen, window is not defined, washed-out textures…).

docs/DECISIONS.mdappend-only · check before changing patterns

The anti-erosion mechanism. A lightweight ADR log: one dated entry per deliberate choice (decision / context / alternatives / consequences). A future session — human or Claude — checks the why before “improving” something, directly countering the failure mode where AI suggestions quietly violate decisions made for a reason3. Seeded with three example entries: JS-not-TS, one canvas per page via a shared wrapper, and zustand as the state bridge. Old entries are never edited, only superseded.

Principles

Four design choices behind the kit

1 · Lean router beats fat file

The root file stays under the adherence ceiling by holding rules + a routing table, not knowledge. Depth lives in docs/ and costs context only on demand.

2 · Hard rules = known failure modes

The always-loaded rules are exactly the bugs Claude (and humans) reintroduce most: SSR boundaries, per-frame allocation, disposal, stray lockfiles.

3 · Decisions outlive sessions

DECISIONS.md preserves the why. Check it before changing a pattern — the cheapest defense against architectural erosion3.

4 · Memory is an explicit step

Don’t hope auto memory catches it. End deep sessions by asking Claude to append durable lessons to the right docs file — synthesis as a habit.

The Bun rules

Three Bun-specific guards are written into the kit so Claude Code doesn’t fall back to npm habits:

  • Bun only. bun for installs and scripts, bunx instead of npx. bun.lock is the only lockfile; any stray package-lock.json is deleted on sight (otherwise a single habitual npm install splits the dependency tree).
  • Runtime caveat. Bun here is the installer and script runner — Next.js itself still executes on the Node runtime by default, so Claude must not “helpfully” add --bun to next commands4. Going full-Bun-runtime later would be a DECISIONS.md entry.
  • Command block rewritten: bun install · bun dev · bun run build · bun start · bun run lint · bun add <pkg> (ask first).
Bun ↔ Next.js runtime compatibility evolves quickly — if you ever switch the runtime itself to Bun, verify current support at that time rather than trusting this snapshot.
How to Use

Bootstrap in three steps

  1. Drop the files in. Unzip into your project root so CLAUDE.md sits beside package.json and docs/ beside it. Commit them — the project file is team memory via source control1.
  2. Run one bootstrap session. Start Claude Code in the project and ask it to read the codebase and fill in ARCHITECTURE.md sections 2–7 with what’s actually there, then correct anything it got wrong. This converts the template into your project’s real theory.
  3. Replace the placeholders. Project name, the styling choice in CONVENTIONS §4 (CSS Modules vs Tailwind — keep one, delete the other), and the three seeded DECISIONS entries, which are examples in the correct format.

The session loop

How knowledge compounds instead of evaporating

The loop the kit is built around — synthesis is an explicit end-of-session step.

Two prompts make the loop concrete:

End of a deep session: “Summarize the durable, non-obvious things you learned this session — one or two lines each — and append them to the right file under docs/. If we made a deliberate choice, add a dated DECISIONS.md entry.”
Start of the next session: just state the task (“continue the particle system”) — the theory is already loaded. For resuming the same conversation instead, claude --continue / claude --resume restore a prior session directly.
