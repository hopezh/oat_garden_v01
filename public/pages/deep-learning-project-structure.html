PyTorch · uv · marimo

Structuring a
deep-learning project

The bare "notebooks + src" sketch is the seed, not the plant. Here is a layout that scales: an installable package at its core, uv managing one lockfile that resolves the right PyTorch build per machine, config as data, and marimo notebooks that import your own code instead of duplicating it.

TL;DR

  • The project is a package (src/<pkg>/), installed editable. Scripts and notebooks are thin callers that import it — logic lives in one place.[3]
  • One uv.lock covers both your machines. [tool.uv.sources] routes torch to the CUDA 12.8 index on Windows (your RTX 5090) and falls back to PyPI on macOS, whose wheel ships the MPS backend.[1][7]
  • marimo joins two ways: as a dev dependency sharing the project env, or as PEP 723 --sandbox notebooks with self-contained, isolated deps.[2][4]
  • Config is composed, not hard-coded: Hydra/YAML groups turn "an experiment" into one small file.[8]
  • Reproducibility is structural — seeded runs, checkpointed state, a device-agnostic backend, and data/ & outputs/ kept out of Git.

01 The full layout

Everything below is one uv project. The pieces that grow independently — the package, the configs, the notebooks, the runs — each get their own home.

Why the src/ package is the whole point

The single biggest difference between a "folder of scripts" and a professional project is that the code becomes an installable package. Once deeptrace is installed (editable), every script, every test, and every notebook imports the exact same deeptrace.models, deeptrace.training, and so on — no sys.path hacks, no copy-pasted cells. The marimo docs make the same recommendation: create a package with uv init --lib and import from it rather than manipulating paths.[3]

⚑

The src-layout rule of thumb. If a piece of logic is used by more than one script or notebook, it belongs in src/deeptrace/. Scripts and notebooks should read like a table of contents for your package, not like the package itself.

02 The pyproject.toml

One declarative file drives dependencies, the build backend, the PyTorch index routing, and tooling. uv sync turns it into a locked, reproducible environment.

pyproject.toml[project]
name = "deeptrace"
version = "0.1.0"
requires-python = ">=3.12"
dependencies = [
    "torch>=2.7",           # >=2.7 first shipped Blackwell / sm_120 wheels
    "torchvision>=0.22",
    "numpy",
    "polars",               # your dataframe stack
    "plotly",               # your charting stack
    "hydra-core",           # config composition
    "pydantic",             # typed config validation
    "tqdm",
    "rich",
]

[project.optional-dependencies]
track = ["wandb"]           # swap for "mlflow" or "tensorboard" as you like

[dependency-groups]         # PEP 735 dev-only groups — never shipped to consumers
dev = [
    "marimo",               # notebooks share this project environment
    "pytest",
    "ruff",
    "ipython",
]

[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

# --- PyTorch wheel routing: one lockfile, the right build per machine --------
[[tool.uv.index]]
name = "pytorch-cu128"
url = "https://download.pytorch.org/whl/cu128"
explicit = true             # only packages that opt in (below) use this index

[tool.uv.sources]
# Windows desktop (RTX 5090 / Blackwell, sm_120) -> CUDA 12.8 build.
# macOS (M4 Pro): no override, so uv resolves from PyPI, whose macOS
# arm64 wheel already contains the MPS / Metal backend.
torch       = [{ index = "pytorch-cu128", marker = "sys_platform == 'win32'" }]
torchvision = [{ index = "pytorch-cu128", marker = "sys_platform == 'win32'" }]

[tool.ruff]
line-length = 100
target-version = "py312"

[tool.pytest.ini_options]
testpaths = ["tests"]

PyTorch wheel routing, explained

PyTorch is awkward to package: its accelerator builds (CPU, CUDA 12.6, 12.8, 13.0, ROCm…) live on a dedicated index rather than PyPI, and the accelerator is baked into a local version suffix.[1] uv's answer is declarative — you name the index with explicit = true, then use [tool.uv.sources] with environment markers to select it per platform.[1] Because your two machines are Windows-CUDA and macOS-MPS, the routing is clean: only win32 pulls the cu128 wheel; macOS silently falls back to PyPI, which is exactly what you want since PyTorch publishes no CUDA builds for macOS.[1]

i

Why cu128 specifically. The RTX 5090 is Blackwell (compute capability sm_120); it requires CUDA 12.8, and PyTorch 2.7 was the first stable release to ship pre-built cu128 wheels with sm_120 kernels.[7] An older CPU/CUDA build will load but refuse to run kernels on the card.

There is also a --torch-backend=auto flag that auto-detects your GPU, but it only works in the uv pip interface — not with uv lock/sync/run — so for a locked project workflow the pyproject.toml routing above is the right tool.[1]

Dependency groups vs. optional-dependencies

  • [project.dependencies] — what your package needs to run for anyone who installs it.
  • [project.optional-dependencies] — feature extras a consumer can opt into (here, track for experiment logging), installed with uv sync --extra track.
  • [dependency-groups] (PEP 735) — developer-only tools like marimo, pytest, and ruff. uv installs the dev group by default on uv sync, and it never leaks into a published wheel.

03 Inside the package

Each sub-package has one job. The split below is what keeps a training run debuggable six months later.

  • data/ — Dataset subclasses, the split/assembly logic, and transform pipelines. Nothing here knows about models.
  • models/ — pure nn.Module definitions plus a small registry so a config string like vit_small resolves to a constructor.
  • training/ — the loop, optimizer/scheduler builders, AMP and grad-accumulation, and callbacks (checkpointing, early stopping). This is where a hand-rolled loop or a Lightning module goes.
  • utils/ — the cross-cutting glue: seeding, checkpoint (I/O of model + optimizer + RNG state), tracking, and the device selector below.

Device selection — your dual-machine glue

Because you move code between a CUDA desktop and an Apple-Silicon Mac, never hard-code "cuda". One helper keeps every script and notebook portable:

src/deeptrace/utils/device.pyimport torch


def get_device() -> torch.device:
    """Pick the best available backend, portably across machines."""
    if torch.cuda.is_available():            # Windows desktop, RTX 5090 (CUDA)
        return torch.device("cuda")
    if torch.backends.mps.is_available():    # Mac mini, M4 Pro (Metal / MPS)
        return torch.device("mps")
    return torch.device("cpu")


def autocast_dtype(device: torch.device):
    """bf16 on CUDA Blackwell; MPS/CPU stay fp32 for stability."""
    return torch.bfloat16 if device.type == "cuda" else torch.float32
⚑

Portability, not just correctness. Route everything through get_device() and move tensors with .to(device). A model that trains on your 5090 then runs unchanged on the M4 Pro is the payoff for never writing a literal backend string.

04 Where marimo fits

marimo notebooks are pure .py files, so they slot into the project like any other module. There are two integration modes — pick per notebook, not per project.[2]

Mode A

Shared project env

marimo is a dev dependency; the notebook runs in the project's .venv and imports your package directly.

  • Same torch build, same deeptrace code as training
  • Launch: uv run marimo edit notebooks/03_results_dashboard.py
  • UI-installed packages go to the project via uv add

Use for: dashboards, evaluation, data exploration, sanity checks — anything that is part of the project.[2]

Mode B

PEP 723 sandbox

Dependencies are inlined in the file header; marimo + uv build a fresh isolated venv on open.

  • Self-contained & shareable — runs anywhere uv is present
  • Launch: uv run marimo edit --sandbox notebooks/sandbox/x.py
  • Your package added as an editable source in the header

Use for: throwaway explorations, examples, and notebooks with odd or conflicting deps you don't want in the main env.[4]

A shared-env notebook that imports your package

This is the whole reason the src-layout matters: the notebook is thin and reactive, and the heavy lifting is your own code. marimo builds a dependency graph from each cell's parameters and returns, so cells re-run in reference order, not top-to-bottom.

notebooks/03_results_dashboard.pyimport marimo

app = marimo.App(width="medium")


with app.setup:                                  # runs first
    import polars as pl
    import plotly.express as px
    from deeptrace.utils.checkpoint import list_runs, load_history  # your package!


@app.cell
def _(mo):
    run = mo.ui.dropdown(list_runs(), label="run")  # reactive control
    run
    return (run,)


@app.cell
def _(run, load_history):
    history = pl.DataFrame(load_history(run.value))  # re-runs when `run` changes
    return (history,)


@app.cell
def _(history):
    px.line(history, x="step", y="loss", color="split")  # live loss curves
    return


if __name__ == "__main__":
    app.run()

A sandbox notebook (isolated deps, editable src)

Running with --sandbox makes marimo track imports and write them into a PEP 723 header — essentially a pyproject.toml inlined at the top of the script — which uv uses to spin up an isolated environment.[4] You can still pull in your own package as an editable source:

notebooks/sandbox/scratch_augmentations.py# /// script
# requires-python = ">=3.12"
# dependencies = [
#     "marimo",
#     "torch>=2.7 ; sys_platform != 'emscripten'",
#     "torchvision",
#     "deeptrace",
# ]
#
# [tool.uv.sources]
# deeptrace = { path = "../../", editable = true }
# ///

import marimo
app = marimo.App()
# ... cells ...
i

Keep notebooks importing, not defining. A marimo notebook enforces one definition per variable across the whole file, which nudges you toward small, reactive cells that call into deeptrace. If a cell grows a real function or class, promote it into src/ and import it back.

05 Configs & scripts

Treat a run's settings as data. Hydra composes small YAML groups into a full config, so "an experiment" is one file you can commit, diff, and reproduce.[8]

configs/config.yamldefaults:
  - data: cifar10        # pulls configs/data/cifar10.yaml
  - model: resnet18      # pulls configs/model/resnet18.yaml
  - trainer: default
  - _self_

seed: 1234
epochs: 50
lr: 3.0e-4

Thin entry points

The script parses config and delegates. All the logic it touches lives in deeptrace, so the same code path is exercised by tests and notebooks.

scripts/train.pyimport hydra
from omegaconf import DictConfig

from deeptrace.data import build_datamodule
from deeptrace.models import build_model
from deeptrace.training import Trainer
from deeptrace.utils.device import get_device
from deeptrace.utils.seed import seed_everything


@hydra.main(version_base=None, config_path="../configs", config_name="config")
def main(cfg: DictConfig) -> None:
    seed_everything(cfg.seed)
    device = get_device()                     # cuda on the desktop, mps on the Mac
    datamodule = build_datamodule(cfg.data)
    model = build_model(cfg.model).to(device)
    Trainer(cfg.trainer, device=device).fit(model, datamodule)


if __name__ == "__main__":
    main()

Override anything from the CLI without editing files — uv run python scripts/train.py model=vit_small lr=1e-3 trainer=debug. Hydra writes each run (resolved config, logs, checkpoints) into a timestamped outputs/ dir, which is why that folder is gitignored.

06 Running it, per machine

The uv and marimo commands are identical on both machines. Only the one-time install and the resolved torch build differ — and uv handles the latter for you from the same lockfile.

powershell# one-time: install uv
powershell -c "irm https://astral.sh/uv/install.ps1 | iex"

uv sync                          # resolves the cu128 torch build for the 5090
uv run python scripts/train.py experiment=baseline
uv run marimo edit notebooks/03_results_dashboard.py

# manual venv activation, if you prefer:
.venv\Scripts\Activate.ps1
terminal# one-time: install uv
curl -LsSf https://astral.sh/uv/install.sh | sh

uv sync                          # resolves the MPS torch build from PyPI
uv run python scripts/train.py experiment=baseline
uv run marimo edit notebooks/03_results_dashboard.py

# manual venv activation, if you prefer:
source .venv/bin/activate

A sandbox notebook is launched the same way on either OS — uv creates its isolated environment on the spot:[6]

either OSuv run marimo edit --sandbox notebooks/sandbox/scratch_augmentations.py

Cross-platform notes

  • The torch build differs; your code doesn't. uv resolves cu128 on Windows and the MPS wheel on macOS from the one lockfile; get_device() then picks cuda vs mps at runtime. Commit uv.lock so both machines agree.
  • A few accelerator-only packages won't resolve on macOS. Anything CUDA-specific (custom Triton kernels, some quantization libs) should be gated behind a marker or an optional group so a Mac uv sync doesn't fail.
  • Sandbox mode needs uv on PATH. The --sandbox feature is uv-only, since it leans on uv's PEP 723 support to build the isolated venv.[4] Install the extra with uv add 'marimo[sandbox]' if you use Sandboxed Home.
  • Commands are identical. Only the uv installer and manual venv-activation syntax differ between the two shells — everything after uv sync is the same.
