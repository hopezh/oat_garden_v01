One core, three shells

How claude.ai (web), the Claude Desktop app, and the Claude Code CLI overlap, where they diverge, which config files carry across them, and how to make them work together.

updated 2026-07-04 web · desktop · cli config portability

TL;DR The shape of it

The three surfaces are shells over a single core — same models, one account, one usage pool. But they split into two config domains, and the desktop app straddles both:

  • Account-synced state (server-side, not files) drives the conversational surfaces: web, Desktop Chat/Cowork, mobile — carrying chats, projects, memory, preferences.
  • Claude Code config (files in ~/.claude/) drives the coding engine: the CLI and the Desktop Code tab — carrying CLAUDE.md, settings, skills, hooks, MCP.
  • Cowork is desktop-only; Design is web + desktop (and CLI via MCP); Claude Code artifacts are Team/Enterprise-only.

The question

Three entry points to Claude get conflated because they share a brain but expose different slices of it. The clean way to reason about them is: one core, three shells — a browser shell, a native-desktop shell, and a terminal shell — each surfacing a different set of capabilities and, crucially, reading from different configuration.

The shared core

All three are windows onto the same underlying system, not separate products with separate brains:

Same models and account. Opus / Sonnet / Haiku, one Anthropic login, one subscription usage pool (or API key). Nothing about the model differs by surface.[4]

Synced state. Conversations, projects, memory, and preferences sync across devices when signed in — a project started on the web is present in the desktop app and on mobile.[1]

MCP as the common connector layer. Web-based connectors like Google Drive and Slack work wherever you use Claude; local MCP servers and desktop extensions are desktop-only.[1]

One agentic engine under Cowork and Code. Claude Code is the developer CLI; Cowork brings the same agentic architecture to the desktop for non-coding knowledge work — framed as “Claude Code for the rest of your work,” and both now share the same computer-use capability.[2][12]

Cowork

The sharpest dividing line. Cowork runs only in the desktop app — never the browser, never mobile — and is paid-plans-only. It is the autonomous, goal-in / deliverable-out mode that works on a folder you grant it.[1] The internal contrast the docs draw: Cowork is a background agent working in a VM with its own environment, while Code has direct access to your local files with each change approved in real time.[3]

Code & artifacts

Claude Code’s native home is the CLI, but the same engine is reachable from the terminal, VS Code, JetBrains, the Desktop Code tab, and the browser at claude.ai/code.[4] The Desktop Code tab additionally offers Local / Remote (cloud) / SSH session environments.[7]

Two things share the name “artifacts.” The classic in-chat artifact you already have everywhere, and the newer Claude Code artifacts (shipped 18 Jun 2026): live, versioned, org-private pages built from full session context — the codebase, connectors, and conversation — available in beta to Team and Enterprise orgs only, from the CLI and desktop app, viewable in any browser.[5]

Design

Claude Design is no longer web-only: it runs on the web at claude.ai/design and from the sidebar in Claude Desktop (web + desktop only, not mobile).[9] The important development is a first-class, bidirectional loop with Claude Code:

DirectionMechanism
Into Design/design-sync from Claude Code pulls your design system in, so Design builds from your real components (repo, design files, or local codebase).
Out of DesignHand off to Claude Code, which continues from your existing work rather than a screenshot — targets “local coding agent” or “Claude Code Web.”
Terminal-nativeAdd the Claude Design MCP server to work entirely from the CLI.

The terminal-native path (OS-agnostic command):

claude mcp add --scope user --transport http claude-design https://api.anthropic.com/v1/design/mcp

then /design-login to sign in. After that you can import a design into your codebase, export code as a live prototype, or let Claude build the whole thing from the terminal.[9]

Also changed

Usage is now unified — Design’s former separate weekly allowance is gone; activity now draws from the same shared pool as chat, Code, and Cowork (so it shows up in ccusage alongside everything else). Export expanded to .zip, PDF, PPTX, Canva, standalone HTML, plus send-to destinations including Vercel, Replit, Lovable, Gamma, Miro, and Wix.[9] Design is codebase-aware and launched Apr 2026 for Pro/Max/Team/Enterprise.[10]

Best scenario for each

claude.ai (web) — quick, low-footprint work from any browser: a chat anywhere, reviewing a Project, a Design prototype, or a cloud Code session not tied to a local checkout.

Desktop app — anything touching local files or local tools, plus Cowork. The only place all three modes, local MCP/extensions, and computer use coexist in one window. Multi-step knowledge work over a folder belongs here.

Code CLI — the real dev loop: full terminal integration, scriptability, hooks, statusline, ccusage, wrapper scripts, per-invocation env control.

Config & settings portability

“Three shells” is slightly misleading here: there aren’t three independent config domains, there are two — and the desktop app is the one place both live side by side. The official docs are explicit that the Code tab and CLI are two clients for the same engine, reading the same configuration files.[7]

Confirmed by the docs: CLAUDE.md / CLAUDE.local.md, MCP servers in ~/.claude.json or .mcp.json, hooks, skills, and settings in ~/.claude.json and ~/.claude/settings.json are all shared between the CLI and Desktop Code tab.[7] Skills specifically converge on one path used by both surfaces.[11]

Asymmetries worth knowing

The MCP story is the sharp edge. The Desktop app loads servers from claude_desktop_config.json into Code-tab sessions alongside ~/.claude.json and .mcp.json — but the standalone CLI does not read claude_desktop_config.json. To pull those in, run claude mcp add-from-claude-desktop. So a server set up for Desktop Chat/Cowork silently appears in the Code tab yet is invisible to claude in the terminal until imported.[7][8]

Two more one-way boundaries: desktop extensions and account state don’t cross into the CLI (no file to carry), and nothing in ~/.claude/ reaches the web or Cowork, because those surfaces don’t run the Code engine. Session JSONL and credentials are machine-local — CLI and Code-tab sessions share configuration but keep separate session histories, which is why ccusage figures are per-machine.[6]

OS paths

The genuinely OS-divergent pieces are file locations and installers. Everything else (the claude mcp commands, /design-sync, /desktop) is identical across platforms.

Config home — ~/.claude resolves to %USERPROFILE%\.claude.[6]

%USERPROFILE%\.claude\settings.json
%USERPROFILE%\.claude.json          # user MCP servers
%APPDATA%\Claude\claude_desktop_config.json

Credentials — stored in ~/.claude/.credentials.json on Windows/Linux — plaintext by default, so key-hygiene setups often encrypt it or inject keys per-call via a wrapper script. Installer — MSIX.[1]

Config home — ~/.claude (i.e. /Users/you/.claude).

~/.claude/settings.json
~/.claude.json                       # user MCP servers
~/Library/Application Support/Claude/claude_desktop_config.json

Credentials — stored in the macOS Keychain rather than a plaintext file. Installer — PKG.[1]

The claude_desktop_config.json paths follow standard OS app-data conventions; the ~/.claude resolution and credential-storage split are documented behavior.

Using them together

The interop is designed as a relay across surfaces:

CLI ⇄ Desktop. Bring a CLI conversation into the desktop app with /desktop, or continue from web or phone — useful when you want the CLI’s credential model for the work but the desktop diff-viewer for review.[4]

Mobile → CLI. Use Remote Control on mobile to send tasks to the Claude Code CLI and reach your local dev environment.[4]

Design → Code. Prototype visually, then hand the bundle to Claude Code to implement — a closed loop from exploration to production.[9]

Cowork vs CLI division of labor. Keep coding in the CLI (where tooling and credentials live); push non-coding multi-step chores — file wrangling, report assembly, doc synthesis — to Cowork rather than hand-driving them in chat.

Usage caveat

Cowork and Code sessions consume limits faster than Chat because multi-step tasks are more compute-intensive — worth watching in ccusage if you route folder-work through Cowork or heavy Design iterations, since all of it now draws from one shared pool.[9]

Practical implications

Env-injected keys & the Code tab

Config files carry into the Desktop Code tab, but launch-time environment injection does not. settings.json, CLAUDE.md, skills, hooks, and statusline config are all read identically by the Code tab — but if an API key is scoped per-invocation through a terminal wrapper, the GUI-launched Code tab won’t inherit it. A Code-tab session runs on whatever persistent /login auth is present, not the wrapper-scoped key. The env block in settings.json would carry — but that’s exactly the persistent exposure such a setup avoids, so terminal wrappers stay the only key-scoped path. Net: Code tab = review/diff on login auth; CLI = workhorse for wrapper-scoped key work, with the full ~/.claude/ toolkit intact in both.

Two auth gates, not one

Claude Code artifacts need a Team/Enterprise seat via /login — the API-key path is excluded — so they stay unavailable on individual plans or API-key-only auth. Claude Design only needs a paid consumer plan; its MCP path uses /design-login (browser sign-in over HTTP to api.anthropic.com), authenticating under that subscription rather than ANTHROPIC_API_KEY — decoupled from any env-injected key wrapper.

The non-portable tier — preferences, styles, Projects, chat memory — is account-bound by design; the closest cross-surface equivalent for the Code engine is CLAUDE.md + skills. Design’s standalone-HTML export complements a local HTML-generation skill rather than replacing it: Design covers the live, team-shared, auto-updating case; a local skill gives a zero-dependency file in your own design system with no org dependency.
