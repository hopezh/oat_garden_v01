Why claude-mem Wasn't Remembering

A Windows debugging story: every memory-capture hook silently died because the plugin couldn't find Bun.
claude-mem v13.11.0Windows 11Claude Code plugin2026-07-19

TL;DR

  • Symptom: claude-mem never recalled anything from previous sessions — its database contained zero observations, ever.
  • Cause: on Windows, every plugin hook failed instantly with '"bun"' is not recognized as an internal or external command. Nothing was ever captured, so there was nothing to recall.
  • Why: the plugin's launcher only trusts a bun.cmd shim (what an npm install creates). With the official installer's bun.exe, it spawns the bare word bun through cmd.exe, which can't resolve it in the hook's restricted PATH.[1]
  • Fix: a two-line bun.cmd shim next to bun.exe. Capture verified working immediately after.
  • Upstream: known open bug (issue #3196) with three fix PRs in flight; no official fix merged yet, and the docs don't mention it.[1][5]

1 · Symptom: a memory plugin with amnesia

After installing the claude-mem plugin (a persistent cross-session memory system for Claude Code) and using it through a full coding-and-debugging session, a later session couldn't retrieve anything about that work. Searching the memory database returned nothing — not for the file that was worked on, not for any related keyword.

First hard evidence: the SQLite database at ~/.claude-mem/claude-mem.db was structurally healthy but completely empty — sdk_sessions = 0, observations = 0, user_prompts = 0, session_summaries = 0. This wasn't a retrieval failure. Nothing had ever been stored.

Crucially, the counts were zero even for the current session — meaning capture was broken right now, not just during the earlier session. That reframed the search: stop looking at search/recall, start looking at ingestion.

2 · Diagnosis: following the pipeline backwards

How claude-mem capture is supposed to work

claude-mem registers Claude Code hooks — small commands the editor fires on lifecycle events (SessionStart, UserPromptSubmit, PostToolUse, Stop). Each hook pipes the event into a launcher script (bun-runner.js), which runs the plugin's worker under the Bun JavaScript runtime. The worker stores events in SQLite and has an AI observer distill them into searchable "observations" that get injected into future sessions.[6]

The evidence trail

  1. Memory search returned nothingQueries for the previous session's work found zero matches.
  2. Database inspection: all tables emptySchema fine, worker running, logs clean — but 0 rows everywhere, including for the live session.
  3. Worker & MCP server were healthyThe background worker started, its HTTP API answered, the search tools loaded. So the storage side was fine — events simply never arrived.
  4. Manual hook test succeededRunning the hook command by hand in a full shell produced correct output (exit 0). The plumbing worked — outside the hook environment.
  5. Session transcripts held the answerClaude Code records hook results in its session transcript files. Every claude-mem hook had logged a hook_non_blocking_error.

The smoking gun

hookName: "SessionStart:startup"   → exitCode 1
hookName: "UserPromptSubmit"       → exitCode 1
hookName: "PostToolUse"            → exitCode 1

stderr: '"bun"' is not recognized as an internal or external command,
        operable program or batch file.

Every hook, every event type, every session — the same one-line failure. Because the errors were non-blocking, Claude Code swallowed them silently and sessions carried on normally, which is why the plugin appeared installed and healthy while capturing nothing.

3 · Root cause: findBun() and the missing shim

What the launcher actually does

The plugin ships a launcher, bun-runner.js, that locates Bun before delegating to it. On Windows its findBun() runs where bun and then makes a fateful choice: it scans the output only for a line ending in bun.cmd. If it finds one, it uses that absolute path. If it doesn't — even though where just proved bun exists — it returns the bare string 'bun' and spawns it through cmd.exe with shell: true.[1]

✅ npm-installed Bun (npm i -g bun)

where bun output includes a bun.cmd shim → launcher uses the absolute path → spawn succeeds regardless of PATH.

❌ Official installer (bun.exe only)

No bun.cmd line → launcher falls back to the bare word "bun" → cmd.exe must resolve it from PATH → in the hook's restricted environment it can't → every hook dies.

The irony: findBun() even has a fallback that checks ~/.bun/bin/bun.exe directly — but it is only reached when where bun fails entirely. Here where succeeded (finding bun.exe), so the broken bare-string branch won. A manual test from a normal terminal masked the bug, because a full user PATH lets cmd.exe resolve bun just fine.

What is a "shim", and why two installs differ

A shim is a tiny wrapper file that stands in for a real program and forwards all arguments to it. When you install Bun via npm, npm auto-generates a bun.cmd shim (Windows batch wrapper) — that's the layout the plugin's happy path expects. The official Bun installer instead places a real bun.exe with no shim, which is exactly the case findBun() mishandles.

4 · The fix: give the launcher the shim it wants

Rather than patching plugin code (which updates would overwrite), the minimal reversible fix is to create the bun.cmd shim the launcher is looking for, right next to the existing bun.exe: 

:: ~\.bun\bin\bun.cmd
@echo off
"%~dp0bun.exe" %*

%~dp0 expands to the directory the .cmd file lives in, so the shim always calls the bun.exe sitting beside it — no PATH dependence at all. Now where bun returns a bun.cmd line, findBun() takes its absolute path, and the spawn can no longer fail on resolution.

Verification

Minutes after creating the shim — with no restart — the live session registered itself (sdk_sessions: 0 → 1) and the worker log showed the AI observer actively processing tool-event batches. Hooks run as fresh processes on every event, so the fix took effect immediately.

Two honest caveats:

  • The earlier session's memory is gone — nothing was ever captured, though its raw transcript still exists on disk.
  • Context injection into new sessions begins once observations exist, so recall starts from the next session onward.

An equivalent alternative fix: npm install -g bun, which creates the same style of shim in the npm prefix.

5 · Upstream status: known bug, fix not yet merged

This exact failure is reported in the official repository and is open as of July 2026, with three candidate fix PRs in flight. The official troubleshooting docs do not cover it — their only Windows-specific note concerns Python.[5] The mirror-image bug (npm's bun.cmd-only layout failing under the old spawn logic) was reported earlier and closed "not planned"; the current bun.cmd preference appears to descend from it — which is precisely why official-installer users break today.[4]

6 · Epilogue: what claude-mem shows at session start

With capture fixed, the payoff appears the next time Claude Code starts in the project (including after /clear or /compact): claude-mem's SessionStart hook — registered in the plugin's hooks.json with the matcher startup|clear|compact — injects a compressed summary of previous sessions' work into the fresh session. Each session starts with an empty context, so this replay is the entire recall mechanism: it is plugin behavior, not native Claude Code behavior.

Tuning or silencing it

Caveat: the displayed text is the injected memory context itself. Silencing it means injecting less memory — it cannot be hidden while kept.

The block is configurable via ~\.claude-mem\settings.json, from mildest to strongest:

OptionSettingEffect
Drop the verbose session summary "CLAUDE_MEM_CONTEXT_SHOW_LAST_SUMMARY": "false" Removes the Investigated / Learned / Completed / Next Steps section; keeps the compact observation index.
Slim down the rest "CLAUDE_MEM_CONTEXT_OBSERVATIONS": "10",
"CLAUDE_MEM_CONTEXT_SESSION_COUNT": "3"		 Fewer observations and sessions listed (defaults were 50 and 10).
Disable for a project entirely "CLAUDE_MEM_EXCLUDED_PROJECTS": "<project>" No capture and no recall for that project — undoes the very pipeline fixed above.

Changes take effect on the next session start; the worker re-reads settings, no reinstall needed. Decision here: configuration left unchanged — the injected block doubles as living proof that capture works.
