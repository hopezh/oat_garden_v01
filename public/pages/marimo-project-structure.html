Reactive Python Notebooks

Structuring a
marimo project

A marimo notebook is pure Python, not JSON — so organizing a project is really organizing a small, well-formed package. Here is the anatomy of one notebook, how to lay out many, and how it all runs across operating systems.

TL;DR

  • A marimo notebook is a plain .py file — Git-friendly, runnable as a script, deployable as an app.[1]
  • Each cell is a function: its parameters are the cells it reads, its return values are what it exposes. marimo wires these into a reactive graph, so execution order follows references, not page position.[1]
  • Lay out a multi-notebook project like a package: notebooks/ for chapters, src/ for shared code.[3]
  • Pick a dependency strategy — one shared environment (simple) or per-notebook sandboxes with inlined deps (isolated).[3]
  • Fully cross-platform (Windows, macOS, Linux); the uv and marimo commands are identical everywhere — only toolchain install and manual venv activation differ.[6]

01 Anatomy of one notebook

Where Jupyter stores an .ipynb JSON scratchpad, marimo stores a plain .py file with a deterministic shape.[1]

The skeleton

notebook.pyimport marimo

__generated_with = "0.x.x"        # marimo version stamp
app = marimo.App(width="medium")  # the App object; every cell hangs off it


with app.setup:                   # (optional) setup cell — runs first
    import numpy as np
    import polars as pl


@app.cell                         # a regular cell
def _():
    import marimo as mo
    return (mo,)                  # names this cell exports to others


@app.cell
def _(mo):                        # params = variables this cell consumes
    slider = mo.ui.slider(1, 100)
    slider
    return (slider,)


@app.cell
def _(mo, slider):
    mo.md(f"Value is **{slider.value}**")
    return


@app.function                     # (optional) reusable top-level function
def calculate(x):
    return x * 2


if __name__ == "__main__":
    app.run()

A cell is a function

This is the defining idea. A cell's parameters are the variables it reads from other cells, and its return tuple is what it exposes to the rest of the notebook. marimo reads those references to build a dependency graph — so cells run in a deterministic order based on variable references, never their position on the page.[1]

The setup cell

The with app.setup: block is guaranteed to run before everything else. It is where imports go when they need to back reusable top-level definitions.

Top-level functions & classes

Definitions marked @app.function and @app.class_definition make the notebook importable — you can pull them into other notebooks or scripts with ordinary Python import.[2] The catch: they may only reference symbols from the setup cell or other top-level symbols, not variables defined inside regular cells.

The run footer

The if __name__ == "__main__": app.run() line lets one file run three ways: marimo edit (interactive), marimo run (as an app with code hidden), and python notebook.py (as a plain script).

!

The one-definition rule. Each variable may be defined in exactly one cell. Coming from Jupyter this trips people up — but it is precisely what keeps the dependency graph unambiguous.[5]

02 Organizing many notebooks

Because each notebook is just a .py file, structuring a multi-chapter project is structuring a small package — and marimo leans into that.

Recommended layout

project treemy-project/
├── pyproject.toml          # project + marimo as a dependency
├── README.md
├── src/
│   └── myproj/            # SHARED code, importable everywhere
│       ├── __init__.py
│       ├── data.py         # loaders, dataframe pipelines
│       ├── viz.py          # reusable plotting helpers
│       └── sim.py          # e.g. simulation wrappers
├── notebooks/
│   ├── 01_intro/
│   │   ├── 01_overview.py
│   │   └── 02_setup.py
│   ├── 02_daylight/
│   │   ├── 01_model.py
│   │   └── 02_results.py
│   └── 03_solar/
│       └── 01_irradiance.py
└── tests/

The marimo docs recommend exactly this split: notebooks in a notebooks/ directory, shared logic in a real package under src/.[3] The reason it matters — marimo resolves imports the way Python does, searching sys.path plus the notebook's own folder. So anything outside that folder must be a properly installed package, not a sibling file reached with a sys.path hack.[4]

Two ways to share code

  • Shared utilities → the src/ package. Data loaders, plotting styles, simulation wrappers — put them in src/myproj/ and install editable (uv init --lib, marimo as a dev dependency; uv workspaces for multiple packages). Then every notebook does from myproj.viz import my_chart.[3]
  • Notebook → notebook reuse. marimo can import the @app.function / @app.class_definition defs from one notebook into another.[2] Handy for a chapter-builds-on-chapter flow, but it couples notebooks — reserve it for genuinely shared notebook logic and push anything stable down into src/.

One environment, or many?

This is the decision that most shapes how a sectioned project feels.

Option A

Single shared env

One pyproject.toml — uv add marimo polars plotly, then uv run marimo edit notebooks/…. Shares dependencies across everything and follows standard Python practice. Best when all chapters run the same stack.[3]

Option B

Per-notebook sandbox

Each notebook inlines its own PEP 723 deps and runs isolated: marimo edit --sandbox nb.py or uv run nb.py. Self-contained, so different chapters can carry different — even conflicting — dependencies.[3]

For varied research work a hybrid fits: a shared project env as the baseline, and sandbox the outliers — e.g. a GPU-heavy deep-learning notebook that should not drag its dependencies into every other chapter.

Ordering, running, publishing

  • Ordering. Use numeric filename prefixes (01_, 02_). Cell execution is a graph, but the human reading order of a book of notebooks comes entirely from filenames — so prefix them.
  • Navigating. Run marimo edit notebooks/ pointed at the directory for a file browser over all chapters, rather than opening one file at a time.
  • Publishing as a book. Do not naively WASM-export each notebook — a hello-world export runs ~18 MB and duplicates per notebook. The maintained fix is the marimo GitHub-Pages template, which shares one assets folder across many notebooks.[7]
ⓘ

Gate expensive cells with mo.stop. For long simulations or model training, put the work behind mo.ui.run_button + mo.stop so reactivity does not re-trigger the whole computation every time you nudge an upstream slider.[5]

03 Platform notes

marimo runs anywhere a recent Python does, and the project workflow is portable — with only a couple of setup steps that differ per OS.

Supported platforms

marimo requires Python 3.10 or newer (through 3.14) and runs on Windows 10 and later, macOS (Intel and Apple Silicon), and all major Linux distributions.[6] The editor itself runs in your browser — Chrome / Chromium is recommended, Firefox works too.

Installing the toolchain

The uv and marimo commands are identical on every OS. Only the one-time uv install and — if you skip uv — manual virtual-env activation differ, shown per platform below.

install uv — powershellpowershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"
install uv — terminalcurl -LsSf https://astral.sh/uv/install.sh | sh

From there the project setup is the same everywhere:

create the project (any OS)uv init --lib my-project
cd my-project
uv add marimo polars plotly
uv run marimo edit notebooks/

If you prefer a plain pip + venv flow instead of uv, the only OS-specific step is activating the environment:

powershellpython -m venv .venv
.venv\Scripts\Activate.ps1
pip install marimo
terminalpython3 -m venv .venv
source .venv/bin/activate
pip install marimo

Cross-platform caveats

  • A few optional SQL deps are Unix-only. Some optional dependencies such as chdb are not available on Windows.[6] marimo's DuckDB-based SQL still works, so this rarely bites.
  • GPU backends differ. On an NVIDIA GPU (Windows or Linux) PyTorch uses CUDA; on Apple Silicon it uses the MPS backend. Keep device selection portable if you move a notebook between machines.
  • Config lives in a standard spot. marimo's config file sits under your platform's config directory (e.g. ~/.config/marimo/marimo.toml); run marimo config show to print the exact path.
