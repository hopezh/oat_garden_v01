Building Dash Apps with AI Coding Assistants

An end-to-end guide to building, serving, and publishing Plotly Dash apps with AI coding agents — focused on Claude (Claude Code CLI and the desktop/web app) and the Gemini CLI.

Dash 4.2 / 4.3 MCP Claude & Gemini CLI Updated 2026-06-24

TL;DR Two MCP capabilities, one workflow

  • Build smarter: connect your agent to the hosted Dash Docs MCP (https://dash.plotly.com/_mcp) so it reads the latest Dash docs instead of hallucinating old APIs.2
  • Steer it: drop a short AGENTS.md in your repo root to lock in architecture, libraries, and house rules.1
  • Serve it: add enable_mcp=True (Dash 4.3+) to turn your finished app's callbacks into tools an agent can call — read and write — with no browser.3
  • Ship it: publish to Plotly Cloud (plotly app publish) and flip on the MCP tab so colleagues connect their own agents.46

Prerequisites: Python 3.x, dash (4.x for the app-as-MCP feature), a free Plotly Cloud account (to authenticate the Docs MCP), and one AI agent — Claude Code, the Claude desktop/web app, or the Gemini CLI.

1Setting up your AI workspace

Productive AI-assisted Dash development rests on two building blocks. Set up both once, and every prompt afterward gets dramatically more reliable:

  1. The Dash Docs MCP server (§2) — connects your agent to live documentation so it can search and read the real, current API instead of guessing from stale training data.2
  2. An AGENTS.md file (§3) — a short project "read-me for your agent" that encodes your architecture, libraries, and house rules, and is fed into the agent automatically as system context.1

Why this matters: Dash ships features faster than model training cutoffs. WebSocket callbacks, swappable FastAPI/Quart backends (Dash 4.2), and the MCP toolkit (Dash 4.3) did not exist when most models were trained — so without the Docs MCP an agent will happily write app.run_server(...) and dash_table.DataTable(...) and other obsolete patterns. The Docs MCP gives it the current docs; AGENTS.md gives it your conventions.6

Tip — docs work for humans and robots. A well-documented project (good docstrings, internal READMEs) is picked up by the agent automatically. If something helps the model, it usually helps your teammates too; build one source of truth, not two.6

2Set up the Dash Docs MCP server

The Dash Docs MCP server is a hosted server Plotly runs for you. There is nothing to install or run locally — your agent connects to it over HTTP and authenticates once in the browser with a free Plotly Cloud account.2

ToolWhat it does
list_pagesLists every documentation page with its URL, name, and description
search_pagesSearches the docs by keyword (page content and component properties)
get_page_as_markdownReturns the full content of a page as Markdown

Public server URL:

https://dash.plotly.com/_mcp
Note on the URL. The docs page templatizes the host as https://<your-dash-enterprise-server>/_mcp because the same instructions serve both Plotly Cloud and self-hosted Dash Enterprise. For the public server use https://dash.plotly.com/_mcp exactly (note the leading underscore in /_mcp). Dash Enterprise customers substitute their own server host.2

2.1 · Connect your agent

Pick your agent — the tabs stay in sync with §6.5 below.

Run one command, then restart Claude Code:

claude mcp add plotly-dash-documentation --transport http --scope user https://dash.plotly.com/_mcp
  • --scope user makes the server available across all your projects (drop it for project-only scope).
  • Restart Claude Code after adding it.
  • Authenticate: type /mcp, select plotly-dash-documentation, choose Authenticate, and sign in with your Plotly Cloud account in the browser.
  1. Open Settings → Connectors → Add custom connector.
  2. Name: Plotly Dash Documentation
  3. URL: https://dash.plotly.com/_mcp
  4. Click Connect and sign in to Plotly Cloud. Set the tools to Always allow so Claude can use them without prompting each time.
Heads-up: custom connectors require a paid Claude plan.

Add the server to ~/.gemini/settings.json (note the key is httpUrl, not url):

{
  "mcpServers": {
    "plotly-dash-documentation": {
      "httpUrl": "https://dash.plotly.com/_mcp"
    }
  }
}

Then start the Gemini CLI and authenticate:

/mcp auth plotly-dash-documentation

Add an HTTP MCP server to your client's MCP config (Cursor, Windsurf, VS Code):

{
  "mcpServers": {
    "plotly-dash-documentation": {
      "type": "http",
      "url": "https://dash.plotly.com/_mcp"
    }
  }
}
Two ways to connect Claude — and they're stored differently. The Claude Code (CLI) and Claude Desktop & Web tabs are alternative paths to the same server — you only need one:
  • CLI (claude mcp add … --scope user) writes a file-based registration into your user config at ~/.claude.json (Windows: C:\Users\<you>\.claude.json) under the top-level mcpServers key. It appears in claude mcp list without a prefix and works in every Claude Code session, even when you're logged out of claude.ai. (Drop --scope user and it lands in a project .mcp.json instead.)
  • The Desktop/Web "custom connector" is stored server-side in your Claude account — nothing lands in ~/.claude.json — and is synced down into the Claude Code CLI, where it shows up prefixed with claude.ai (e.g. claude.ai Plotly Dash Documentation).
So the prefix tells you the source: claude.ai … = account connector (synced, no local file entry); no prefix = CLI / file registration (in ~/.claude.json or a project .mcp.json). If you set up both, you'll see the Dash server twice and get duplicate tools — harmless, but remove one to de-clutter: claude mcp remove plotly-dash-documentation --scope user for the CLI entry, or delete the connector in claude.ai → Settings → Connectors.

For example, with both set up, claude mcp list shows the Dash server twice — once claude.ai-prefixed (the connector) and once unprefixed (the CLI entry you just added), both pointing at the same URL:

claude mcp list
claude.ai Plotly Dash Documentation: https://dash.plotly.com/_mcp - ✔ Connected
claude.ai Notion: https://mcp.notion.com/mcp - ✔ Connected
claude.ai Google Drive: https://drivemcp.googleapis.com/mcp/v1 - ! Needs authentication
claude.ai Gmail: https://gmailmcp.googleapis.com/mcp/v1 - ! Needs authentication
claude.ai Google Calendar: https://calendarmcp.googleapis.com/mcp/v1 - ! Needs authentication
my-local-server: http://localhost:3001/mcp (HTTP) - ✘ Failed to connect
plotly-dash-documentation: https://dash.plotly.com/_mcp (HTTP) - ! Needs authentication

Which one survives depends on how you're logged in. The two approaches differ in visibility depending on your Claude Code authentication:

  • Personal subscription (claude.ai login). Both show up. The account connector is synced down (claude.ai-prefixed) and the CLI/file registration is loaded — hence the possible duplicate above.
  • Organization-issued API key (ANTHROPIC_API_KEY, or ANTHROPIC_AUTH_TOKEN / apiKeyHelper / Bedrock / Vertex). Only the CLI / file registration is visible. Account connectors are fetched only when your active auth is the claude.ai subscription; they are not loaded under an API key, even if you previously ran claude /login. The claude.ai-prefixed Dash connector simply disappears, leaving just the unprefixed plotly-dash-documentation entry.

Takeaway: if you log in with a company API key, register the Dash MCP via the CLI (claude mcp add) — the account connector won't be available. For teams, an admin can push it to everyone regardless of auth method via managed MCP (managed-mcp.json).

2.2 · Authentication & access

  • All clients authenticate with your Plotly Cloud account in the browser the first time a tool is used. (Create one free.)
  • Open-source Dash documentation is available to everyone once authenticated.
  • Documentation for enterprise libraries (Dash Design Kit, Snapshot Engine, Dash Embedded, etc.) requires a Plotly Cloud subscription with an Enterprise plan.
  • The Docs MCP authenticates via Plotly Cloud only — it is not supported for Dash Enterprise login.

2.3 · Verify it works

Ask your agent something only the current docs would know, and watch it call a tool:

"Using the Plotly Dash documentation MCP, update this app to use the new Dash WebSocket callbacks instead of dcc.Interval."

You should see the agent call search_pages / get_page_as_markdown (e.g., for "websockets") before it writes code. If it does, the server is wired up correctly.8

No-MCP fallback: every page on dash.plotly.com has a "Markdown" pop-up — copy a single page's Markdown and paste it into any chat without setting up the MCP at all.

3Use the AGENTS.md file

AGENTS.md is a file in your project root that is automatically fed into your agent's prompts as system context. Think of it as a README written for your coding agent: it states your architecture, tech stack, preferred libraries, and the patterns you want enforced. It layers on top of the Docs MCP — the MCP supplies general Dash knowledge, AGENTS.md supplies your project's conventions.1

Claude Code, the Claude desktop/web app, the Gemini CLI, Cursor, and Windsurf all read an AGENTS.md automatically. (Some setups also use CLAUDE.md / GEMINI.md; AGENTS.md is the cross-tool convention.)

3.1 · A ready-to-use template

Copy this into AGENTS.md, then delete anything that doesn't apply (e.g., drop the Dash Enterprise or caching sections if you aren't using them):

## File Structure
my-dash-app/
├── app.py                # Main application file
├── assets/               # Static files (CSS, images, favicon)
├── pages/                # Multi-page app routes
│   ├── home.py
│   └── analytics.py
├── requirements.txt      # Python dependencies
└── AGENTS.md             # This file

# If deploying to Plotly Cloud, also add:
└── plotly-cloud.toml     # Build configuration (optional)

# If deploying to Dash Enterprise, also add:
├── Procfile              # Process declarations (required)
├── project.toml          # Build configuration (optional)
└── Aptfile               # System packages (optional)

## General Architecture
- Global Variables: Never use global variables to store user-specific state. All mutable
  state must live in the client browser using `dcc.Store` or URL parameters.
- Server Variable: Make sure the app file always exposes a server variable: `server = app.server`
- Dash Pages: Use `dash.page_registry`, keep all pages in a `pages/` directory, and register
  each page with `dash.register_page(__name__)`. (If Snapshot Engine is used, do not use Dash
  Pages; use callback routing instead.)
- App IDs: Prefer descriptive IDs like "sales-filter-dropdown" over "dropdown-1". IDs must be
  unique across the entire app, including all pages.
- Loading Data: Load data inside callbacks, not at import time. Data loaded at startup won't
  refresh until the process restarts.
- Server-side Filtering: Filter, aggregate, and paginate data in Python before passing it to
  graphs or AgGrid.
- Pin Dependencies: Specify minimum or exact versions for dash, plotly, and component
  libraries in requirements.txt to avoid breaking changes on deploy.

## Callbacks
- Dataset Size: Use `dcc.Store` only for lightweight state (max ~5MB). Do not pass massive
  datasets through `dcc.Store` if they can be cached server-side.
- Caching: For large datasets or expensive operations, implement server-side caching using
  `flask_caching` with the `@cache.memoize()` pattern.
- Input IDs: Every Input, Output, and State ID must exist in the layout when the callback
  fires; set `suppress_callback_exceptions = True` for dynamic or multi-page layouts.
- Prevent Initial Call: Use `prevent_initial_call=True` for button-triggered actions.
- Prevent Unnecessary Updates: Return `dash.no_update` when an output should stay unchanged.
- Keep Callbacks Focused: One callback per user interaction when possible.
- Loading Spinners: Show a spinner while data loads by wrapping components in `dcc.Loading`.
- Background Callbacks: For work that takes more than a few seconds, use `background=True`.

## Layout and Styling
- Custom Style Sheets: Place core styles in CSS files in the `assets/` directory.
- Theme File: Use a shared `theme.py` for color constants and spacing.
- Inline Styles: Use only for dynamic, runtime-computed values; avoid static inline styling.
- Code Format: Run `black` for Python and Prettier for CSS.

## Charts and Components
- Graphing Library: Use `plotly.express` for charts first — it is simpler and covers most
  cases. Switch to `plotly.graph_objects` only when you need fine-grained control.
- Component Libraries: Prioritize in this order — Dash Design Kit (if you have access), then
  Dash Core Components + Dash HTML Components, then Dash Mantine Components, then Dash
  Bootstrap Components if required.
- Data Tables: Never use `dash_table.DataTable`; use `dash.AgGrid()` instead.
- AgGrid Config: Set `dashGridOptions`, `columnSize="responsiveSizeToFit"`, and a
  `defaultColDef` with filtering and sorting enabled.

## Avoid Hallucinations
- Never use `app.run_server`; only use `app.run`.
- Never use the obsolete `app.validation_layout`.
- Always use modern imports:
  `from dash import Input, Output, State, callback, clientside_callback, no_update, ALL, MATCH`
  (never import items from `dash.dependencies` individually).
- Never write blocking `time.sleep` loops inside a callback; use `dcc.Interval` (or a task
  queue like Celery/Redis) instead.
- Never use `dash_table.DataTable`; use `dash.AgGrid()`.
- Never put secrets, API keys, or credentials in layout code or `dcc.Store`.

3.2 · Tips from the Plotly team

From Plotly's own webinar walkthrough — practical gotchas when writing an AGENTS.md:6

  • Keep it short — aim for ~100 lines max. Every prompt re-sends the file, so a long file burns tokens on every turn. Keep it concise and non-repetitive.
  • Write it yourself. Human-written instructions are clearer for the agent to consume; LLM-generated AGENTS.md files tend to be vague and bloated.
  • It takes precedence. If an AGENTS.md instruction conflicts with what the agent finds in the docs, the AGENTS.md usually wins — use it to lock in non-negotiables.
  • Encode the hallucinations you actually see. If your agent keeps reaching for an old pattern, add an explicit "never do X" line.
  • Prune ruthlessly. Start from the template and delete every section you aren't using.

4Structure a multi-page Dash app for AI-assisted development

A clean, conventional structure is what lets an agent navigate and extend a project without getting lost. The structure below is the one the Docs MCP and AGENTS.md assume.1

4.1 · Recommended layout

my-dash-app/
├── app.py                # Entry point: app = Dash(...), use_pages=True, server = app.server
├── assets/               # CSS, images, favicon (auto-loaded by Dash)
│   └── styles.css
├── pages/                # One file per route, auto-registered
│   ├── home.py
│   └── analytics.py
├── theme.py              # Shared colors / spacing constants
├── requirements.txt      # Pinned dependencies
└── AGENTS.md             # Agent context

4.2 · Architecture rules that make AI editing reliable

  • Use Dash Pages for routing. Set use_pages=True, keep one file per page in pages/, and register each with dash.register_page(__name__). The router is automatic — no manual URL callback.
  • Expose server = app.server. Required by every deployment target (gunicorn, Plotly Cloud, Dash Enterprise).
  • Descriptive, globally-unique IDs. "sales-filter-dropdown", not "dropdown-1". Unique across all pages — this is how an agent (and the MCP server later) maps callbacks to UI.
  • Load data inside callbacks, not at import time. Module-level pd.read_csv(...) freezes data until restart and breaks multi-worker deployments.
  • Filter, aggregate, and paginate in Python before the data reaches a graph or AgGrid.
  • No global mutable state. Keep per-user state in dcc.Store or URL params — servers run multiple workers and share nothing in memory.
  • Keep page callbacks with their page. Put each page's callbacks at the bottom of that page's file, so a feature lives in one place.

4.3 · Why this helps the agent

AI agents tend to over-engineer — splitting code into many tiny files or stuffing everything into one giant file. A predictable pages/ layout with descriptive IDs and localized callbacks gives the agent obvious seams to work along, so its edits stay surgical and its mental model matches yours. It's always easier to add code than to remove it, so a tidy skeleton pays off on every later prompt.6

5General tips for AI-assisted development

5.1 · Build in small, verifiable phases

The single biggest lever is to iterate slowly. Plotly's own demo builds an app in three deliberate passes rather than one mega-prompt:6

  1. Scaffold the shell — pages, layout, sidebar, placeholder charts. Explicitly say "no callbacks, no data processing, no interactivity yet."
  2. Wire the data & callbacks — connect filters to charts, load and filter data. Verify interactivity.
  3. Polish the theme last — colors, fonts, spacing. Doing this last avoids the agent re-overriding styles while it's still changing structure.

5.2 · Prompting checklist

  • Reference the Docs MCP explicitly at least once: "reference the Dash docs via MCP."
  • Point at your AGENTS.md: "follow the guidelines in AGENTS.md."
  • Provide sample data. Attach a CSV or describe the schema so the agent picks suitable charts.
  • Describe callback relationships. Spell out how callbacks should chain (e.g., "filter dropdown → update store → redraw both charts").
  • Include requirements.txt so the agent matches your existing dependencies and versions.
  • Iterate visually. Run the app, describe what you see and what you want different — don't prompt blind.
  • Specify your target (Plotly Cloud vs Dash Enterprise) — the deploy workflow differs.
  • Specify your component libraries (e.g., Dash Mantine vs Dash Bootstrap).
  • Be specific when theming. "Apply a pastel palette, a minimalist font, lighten the sidebar, reduce padding" beats "make it look better."

5.3 · Working with large / existing codebases

The same approach scales to a 500-file app you've maintained for years — you just have to be more precise. Work one file or one feature at a time. Vague, whole-app prompts ("make my app faster", "why is this broken?") don't work; narrow, well-scoped prompts do.6

6Use Dash apps as MCP servers for AI agents

The second half of Dash + MCP flips the direction: instead of an agent helping you build the app, your finished app becomes a set of tools an agent can call. Your Dash callbacks already encapsulate data access, filtering, and modeling logic — enable_mcp turns each one into an MCP tool, so an agent can query your data and drive your app without a browser.3

Requires Dash 4.3.0+ (pip install -U dash; release candidate: pip install dash==4.3.0rc0). Documented at dash.plotly.com/dash-mcp.

6.1 · Why route an agent through your app instead of handing it raw data?

  • Accuracy over hallucination. LLMs are bad at crunching raw numbers but great at calling a function that returns a correct answer. Your callbacks are those functions.
  • Governed access. If your app sits on a 100-GB data lake, you can't paste it into a prompt. Your existing filters and access controls let the agent pull only the right subset.
  • Fewer tokens. Calling a tool that returns an aggregate is far cheaper than streaming a whole dataset into context.
  • Callback chaining for free. An agent can pull data from one callback, pass it to a model in another, and get an accurate end-to-end result.6

6.2 · Turn it on

from dash import Dash

app = Dash(__name__, enable_mcp=True)

That's the whole change. When the app runs, an MCP endpoint is served at /_mcp (e.g. http://localhost:8050/_mcp) over Streamable HTTP.

  • Change the path with mcp_path="...".
  • Or configure via environment variables: DASH_MCP_ENABLED and DASH_MCP_PATH.

What gets exposed automatically:

App elementExposed asNotes
CallbacksToolsIncluding pattern-matching and background callbacks
Layout / components / pages / clientside callbacksResources (dash://layout, …)So the agent understands your app's shape
Callback returning a dcc.Graph figuretool result → PNG imageRendered via kaleido, returned as image content
Callback returning table data (DataTable.data, AgGrid.rowData)tool result → Markdown tableLLM-friendly text

Type hints on your functions inform each tool's input schema, so annotate your callbacks and custom tools.

6.3 · Add custom tools with @mcp_enabled

Not every useful tool maps to a UI callback. Decorate any plain Python function to expose it as a tool — even in an app with no front end at all (a pure "agent toolkit" Dash app):

from dash import Dash
from dash.mcp import mcp_enabled

app = Dash(__name__, enable_mcp=True)

@mcp_enabled(name="get_sales", expose_docstring=True)
def get_sales(region: str, quarter: str) -> dict:
    """Return total sales for a region and quarter."""
    df = query_warehouse(region, quarter)   # your governed data access
    return {"region": region, "quarter": quarter, "total": float(df["amount"].sum())}

@mcp_enabled works bare (@mcp_enabled) or parameterized (@mcp_enabled(name="...", expose_docstring=...)).

6.4 · Control what's exposed with configure_mcp_server

from dash.mcp import configure_mcp_server

configure_mcp_server(
    include_layout=True,
    include_callbacks=True,
    include_clientside_callbacks=True,
    include_pages=False,            # e.g. hide page registry
    expose_callback_docstrings=True # off by default
)

6.6 · Read and write

MCP isn't read-only. If you expose tools (or callbacks) that write — adding a to-do, updating a record, kicking off a job — agents can take actions through your app, turning a CRUD Dash app into something an agent can operate. Expose write tools deliberately.6

6.7 · Security notes

  • Stateless by design. Calling a tool executes a callback and returns its result to the agent — it does not update a user's browser session.
  • Docstrings are private by default. Callback docstrings are not exposed unless you opt in via expose_callback_docstrings=True.
  • You control the surface. Use configure_mcp_server(...) to limit what's shared.
  • Don't rely on obscurity. Tool/callback names are visible to the agent. Enforce real access control through authentication, not by hiding inputs.

6.8 · Publish the MCP server (hosted, authenticated)

Running locally is great for development, but your end users — often non-technical — just want to connect their own agent to your app. Publishing to Plotly Cloud makes that turnkey:6

  • After publishing (§7), open the app's MCP tab in its Plotly Cloud settings and enable MCP — a checkbox, no code changes required. (This also works for apps built in Plotly Studio.)
  • Plotly Cloud wires up the OAuth sign-in flow for you. Only users who already have access to the app (per your existing sharing settings) can connect the MCP server.
  • Viewers see an "AI agent" / Connect button on the hosted app with copy-paste instructions for their client, so you don't have to hand-write setup docs.
Hosting elsewhere? For Databricks or Posit Connect there is no built-in MCP auth — an unauthenticated app can be connected, but to authenticate it you'd roll your own (the toolkit supports the OAuth2 MCP spec). MCP auth for Dash Enterprise is on the roadmap. Plotly Cloud is the recommended, integrated path today.6

7Publish AI-generated apps

There are two destinations. Plotly Cloud is the fastest path (and the one with integrated MCP auth); Dash Enterprise is for regulated / on-prem needs. In both cases you can often just tell your agent "deploy this to Plotly Cloud" and let it run the commands via the Docs MCP.4

# 1. Install the cloud CLI (quote the brackets so the shell doesn't glob them)
pip install "dash[cloud]"

# 2. Log in (opens a browser OAuth flow)
plotly user login

# 3. Publish (name it on first publish so the agent isn't prompted interactively)
plotly app publish --name "Q1 Sales Dashboard"

# 4. Check status
plotly app status

# Local development run
plotly app run
  • After the first publish, your app's name/config is saved in plotly-cloud.toml, so later plotly app publish runs need no flags.
  • Sharing: in the app's Cloud settings set "anyone with the link can access," or restrict to specific users — those same permissions gate the MCP connector (§6.8).
  • Free tier: one app + public sharing, no credit card. Paid plans add private sharing, custom URLs, and more apps.
  • Compliance: Plotly Cloud is SOC 2 and ISO 27001 certified (also ISO 27701 / 42001).4
# 1. Install enterprise libraries from your server's package index
pip install dash-enterprise-libraries --extra-index-url <your-dash-enterprise-url>/packages

# 2. Log in to your Dash Enterprise host
de --host your-dash-enterprise.example.com login

# 3. Deploy (path defaults to ., name defaults to the folder)
de deploy . --name my-dashboard

# 4. Status & logs
de apps status --name my-dashboard
de apps logs   --name my-dashboard --type build
de apps logs   --name my-dashboard --type runtime

A Procfile is required for Dash Enterprise — without it the app won't start:

web: gunicorn app:app --workers 4
Version note: use app:app for Dash 3.1.0+; for Dash 3.0.4 and earlier use app:server (web: gunicorn app:server --workers 4). Optional files: project.toml (build config), Aptfile (system packages).5

8End-to-end: build, serve, and ship in one sitting

A realistic flow that ties the whole guide together:

  1. Set up the Docs MCP (§2) and drop an AGENTS.md in your project (§3).
  2. Scaffold — "Build a sales dashboard from data.csv. Reference the Dash docs via MCP and follow AGENTS.md. Two pages (home, analytics), a sidebar of filters. No callbacks or data processing yet."
  3. Wire data — "Add the data to the charts and link the filters using callbacks. Small dataset — no caching needed."
  4. Theme — "Apply a pastel palette and a minimalist font, lighten the sidebar, reduce padding, add contextual colors to the data cards."
  5. (Optional) Make it agent-native — add enable_mcp=True (§6) so the finished app's callbacks become tools.
  6. Ship — "Deploy this to Plotly Cloud." The agent runs plotly app publish (§7).
  7. (Optional) Flip on the MCP tab in Plotly Cloud so colleagues connect their own agents (§6.8).

That's a complete, shareable, AI-friendly Dash app — built, served, and published with an agent in the loop the whole way.8
