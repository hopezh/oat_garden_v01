Rendering Jupyter Notebooks in Zed Preview

Turning on Zed's experimental native .ipynb editor on macOS — the feature flag, the environment variable, the folder-not-file trick, and the safer alternatives when the renderer isn't enough.

▸ TL;DR

  • Zed hides a half-built native notebook editor behind the notebooks feature flag plus the LOCAL_NOTEBOOK_DEV=1 env var.2
  • Add the flag in settings.json, fully quit Zed, then launch from the terminal opening the project folder — not the file, with the env var set for that launch.2
  • Expect rough edges: no cell deletion, no way to kill a running cell, awkward DataFrame printing.2 Interactive Plotly HTML still won't render.1
  • For real pandas/polars work, a Jupytext-paired .py↔.ipynb workflow is the more dependable path today.7

Overview

What the feature actually is, how it differs from the REPL you may already run, and how finished it is.

What the feature is

Zed ships an in-progress native .ipynb editor gated behind a notebooks feature flag and a LOCAL_NOTEBOOK_DEV=1 environment variable. When it engages, the notebook renders as real cells with visual boundaries — you can add code and markdown cells and execute them inline — rather than displaying raw JSON.2 A native .ipynb UI with rich media, inline plots, cell reordering and kernel assignment is exactly what data-science users have been asking Zed to build.3

REPL vs native notebook

These are two different things, and it's easy to conflate them:

Current state & limitations

It's genuinely half-built rather than merely unpolished — treat it today as a "read my notebooks and make quick edits" experience, not a Jupyter replacement.2

CapabilityStatusNote
Render cells inline✓Bordered code / markdown cells
Add & run cells✓Executes against a kernel
Delete a cell from UI✗Drop to JSON, remove the cell block
Kill a running cell✗No interrupt control yet
DataFrame as last expression✗Prints awkwardly
Interactive Plotly HTML✗Use JupyterLab for this1

The feature is also version-sensitive and has regressed between releases — notebooks that rendered fine have reverted to plain JSON after a version bump despite "notebooks": "on" staying set.2 Reports from different version lineages can therefore mislead.

Setup on macOS

Assuming Zed Preview is installed at /Applications/Zed Preview.app and you're signed in via GitHub.

Prerequisites

  • Zed Preview installed — Preview installs alongside stable, so the two channels coexist. Install command differs by OS (below).4
  • Signed in via GitHub (needed because the flag may be a private-beta feature — see Channels & private beta).5
  • A project folder containing at least one .ipynb, with a kernel available (for a uv-per-project setup, the project's ipykernel).

Install Zed Preview:

Homebrew cask — installs Zed Preview.app next to stable:4

brew install --cask zed@preview

No Homebrew on Windows — use winget with the .Preview package id (requires Win 10 1809+ or Win 11). The installer wires up PATH automatically, so no cli: install step is needed:10

winget install --id ZedIndustries.Zed.Preview --exact

Or download the preview .exe from Zed's preview releases page. Update later with winget upgrade --id ZedIndustries.Zed.Preview --exact.10

1

Add the feature flag

In Zed Preview, press Cmd + , to open settings.json and merge in the feature_flags block. Opening settings from within Preview guarantees you're editing the file that build reads.2

{
  "feature_flags": {
    "notebooks": "on"
  }
}

This step is identical on every OS, so it stays a plain code block.

2

Fully quit Zed

Not just closing the window. This matters twice: the feature flag is read at startup, and Zed snapshots its environment at launch, so the env var in the next step won't be seen unless the process starts fresh with it already set.1 A window reload is not enough — it must be a full relaunch, and the quit gesture differs by OS:

Press Cmd + Q. Closing the window alone leaves the app running, so its old environment persists.

Closing the window doesn't guarantee the process ends. Confirm no zed.exe lingers (Task Manager, or taskkill /IM zed.exe /F) — or skip the worry entirely by using zed --foreground . in the next step, which forces a fresh process rather than reusing a background one.1

3

Launch from the terminal — with the env var, opening the folder

This is the step that trips everyone up. Opening a .ipynb directly renders it as raw JSON; you must open the containing folder and then open the notebook from Zed's file tree.2

⚠ Folder, not file

The trailing . (the project directory) is essential. Passing the notebook path as the argument — zed notebook.ipynb — will not trigger the renderer.2

The exact invocation differs by platform. This conversation covered a prior Windows attempt and the current macOS setup:

Most reliable — point straight at Preview's CLI binary and prefix the env var, so it can't collide with whichever channel your plain zed launches:8

cd /path/to/your/project
LOCAL_NOTEBOOK_DEV=1 "/Applications/Zed Preview.app/Contents/MacOS/cli" .

Shorter, if your zed command points at stable — route to Preview explicitly:9

LOCAL_NOTEBOOK_DEV=1 zed --preview .

In PowerShell, set the variable in the session, then launch with the folder. --foreground was the outstanding fix to try on the earlier Windows stable build:1

$env:LOCAL_NOTEBOOK_DEV = "1"
zed --foreground .

Same env-snapshot rule applies: Zed on Windows also captures its environment at launch, so set the variable before the launch and start a fresh process.1

Then confirm the variable is actually set for that shell before relying on it:

echo $LOCAL_NOTEBOOK_DEV   # should print: 1
echo $env:LOCAL_NOTEBOOK_DEV   # should print: 1
4

Open the notebook & assign a kernel

With the project folder open, click your .ipynb in the file tree. It should render as cells with visual boundaries rather than JSON. Assign your kernel — for a uv-per-project setup, pick the project's ipykernel from the kernel selector, same as with your # %% REPL workflow.2

Troubleshooting — still showing JSON?

  • Opened the folder, not the file at launch — re-confirm the . was the argument.2
  • The env var was set for that launch — run the verify command above in the same shell first.
  • You did a full Cmd + Q, not a window reload, after editing settings.1
  • You're genuinely in Preview, not stable — the app menu should read "Zed Preview," since the flag behaves differently across channels and can regress between versions.2
  • Access may be gated server-side. If flag + env var + folder-launch still yields nothing, the flag might be a private beta your account isn't registered for — config alone won't unlock it.5

Alternatives

Two pragmatic paths for when you want to get work done rather than test a feature.

The lighter option — a syntax-only viewer

A community extension, zed-jupyter-viewer, adds notebook-aware syntax highlighting, cell navigation via the Outline panel (Cmd + Shift + O), and folding of cells, outputs and metadata. But it is explicitly not a renderer — .ipynb files still display as structured JSON text, because Zed currently exposes no dedicated API for custom cell rendering.6 Useful for glancing at a notebook, not for running one.

The robust option — a Jupytext-paired workflow

Keep a .py file — which Zed edits beautifully and runs cell-by-cell through the REPL you already have — synced to an .ipynb via Jupytext. Changes round-trip safely between the two, it's git-friendly (you version the text file instead of large JSON diffs), and it's driven through Zed's task system.7 This sidesteps the whole experimental-rendering question and plays to Zed's existing strengths.

The only OS-divergent line is activating the virtualenv:

python -m venv .venv
source .venv/bin/activate
pip install jupytext
# pair an existing script to a notebook:
jupytext --set-formats py,ipynb your_script.py
jupytext --sync your_script.py
python -m venv .venv
.venv\Scripts\Activate.ps1     # PowerShell  (use activate.bat for cmd.exe)
pip install jupytext
# pair an existing script to a notebook:
jupytext --set-formats py,ipynb your_script.py
jupytext --sync your_script.py
Caveat

It still won't give you interactive Plotly HTML output — that remains the one thing Zed's REPL / notebook path can't do, and JupyterLab's web UI is the fallback there.1

Channels & private beta

Preview is the better channel to test on: it's the weekly release that may contain experimental functionality and can experience reverts of recently-added features, and during private betas Zed prioritizes updates to the preview channel.5 Note that a single cli: install writes one zed symlink — running it from Preview overwrites the stable one, since they share the name. Pointing directly at the Preview binary (as in step 3) avoids disturbing whichever channel your plain zed launches.8

When a feature is in private beta, your Zed user record must be registered to that flag; you sign in via GitHub, and if you're not associated with the flag the related UI stays hidden. Some users have found beta features occasionally reachable on stable, but Preview is where they land first.5
