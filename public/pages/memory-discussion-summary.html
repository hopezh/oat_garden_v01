1 How it started: the yarn / npm mistake

The thread didn't begin as a question about memory at all. It began with a wrong recommendation. [1]

What went wrong

Asked how to run a React Three Fiber starter project, I read its package.json, saw standard Vite scripts ("dev": "vite"), checked the installed Node/npm versions, and then handed over npm install / npm run dev. I never looked for a lockfile.

The catch. The folder contained a yarn.lock and no package-lock.json — so the project uses Yarn. Using npm install would have generated a competing package-lock.json and an inconsistent dependency tree. The fix was a one-line directory listing I skipped. [1]

The correction

The right commands respect the lockfile. Since this project's lockfile is Yarn's, the install/run is OS-agnostic:

cd "...\r3f_ultimate_guide\Ch03_22_physics\22-physics-starter"
yarn install     # installs deps from yarn.lock
yarn dev         # starts the Vite dev server (http://localhost:5173)

When the user asked how I'd "forgotten" to use yarn, the honest answer was: I let package.json's scripts stand in for the whole picture and assumed rather than verified. That correction is what got written to memory. [1]

2 How the lesson was "saved to memory"

Memory here is not a database or a cloud service — it is just plain Markdown files written to local disk with the ordinary Write tool. [2]

The two files written

MEMORY.md The index / table of contents One line per memory, loaded into context at the start of every session

The fact file's frontmatter looked like this:

---
name: detect-package-manager-from-lockfile
description: Before giving install/run commands for a JS
  project, detect the package manager from its lockfile
metadata:
  type: feedback
---

Before recommending install/run commands ... check for a lockfile
(yarn.lock → yarn, pnpm-lock.yaml → pnpm, package-lock.json → npm ...).
Do NOT default to npm just because package.json has standard scripts.

**Why:** ... recommended npm install for a project that had a yarn.lock.
**How to apply:** list the directory for a lockfile in the same step
as reading package.json, then give matching commands.

How it gets used later

STEP 3

Key nuance. The actual fact stays out of context until needed — only the index is always loaded. And it's a note-to-self for future sessions, not a live setting; nothing enforces it automatically. It works by being surfaced back and then followed. [2]

3 Where it lives on disk

Everything sits under the user home directory, in a per-project folder whose name is derived from the project's absolute path: [2]

C:\Users\hopez\.claude\projects\C--Users-hopez-Downloads-dev\memory\
        │                        │
        │                        └─ working dir "C:\Users\hopez\Downloads\dev"
        │                           with separators flattened to dashes
        └─ user home, NOT inside the project repo

Two consequences flow directly from this location: it is not part of the git repo, and its folder name is tied to this machine's absolute path. Both matter for the next question. [3]

4 Does it travel to another computer?

Short answer: no, not by default. [3]

Why it's lost

ReasonEffect
It's under ~/.claude\, outside the projectNever committed or pushed — cloning the repo elsewhere brings none of it.
Folder name is path-derivedOn a machine where the project lives at e.g. D:\code\dev, the harness looks under a different folder name and finds nothing — even copied files would need the matching path-derived folder.

Options if you want it to follow you

ApproachHowTrade-off
Cloud-sync ~/.claudePut it in OneDrive / Dropbox / gitSimplest; syncs all projects. Path-derived folder names must still match.
Commit into the repoMove the fact into a project CLAUDE.mdTravels with git push/pull, works at any path. Best for project-specific facts.
Manual copyCopy the memory\ folder when switchingTedious; folder name must match the new machine's path.
Recommendation given. For this particular "use yarn / detect from the lockfile" fact, the cleanest home is a CLAUDE.md at the repo root — it's project-specific, gets pushed, and works on any machine at any path. Memory under ~/.claude is better for cross-project habits and things you don't want in the repo. (The user chose to leave it as-is.) [3]
