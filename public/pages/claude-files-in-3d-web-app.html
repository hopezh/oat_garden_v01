Field Manual · Claude Code × 3D Web

Wiring Claude Code into a multi-page 3D web app.

Stack · Bun + Vite + Next.js + R3F Sections · 13 Theme · light / dark Version · v1.0

A reference layout for organizing Claude Code inside a Bun + Vite + Next.js + React Three Fiber project, tuned for clarity, modularity, and runtime performance. Part one lays out the application and explains where every Claude-related file belongs. Part two covers the rules, skills, and agents that make day-to-day 3D work faster — without your .claude/ directory turning into a junk drawer.

PART A · FOUNDATIONS / 01

The stack at a glance.

Four tools that overlap in confusing ways unless you name their jobs precisely. Next.js owns the production build and routing; Vite is a side rig for isolated 3D component work; Bun ties everything together as runtime, package manager, and test runner.

bun
Package manager, script runner, and JS runtime. One lockfile, fast installs, and bun test / bunx for tooling.
next.js
App Router framework. Owns routing, the multi-page structure, SSR/RSC shell, and the production bundle.
vite
Isolated sandbox for building & profiling R3F components in seconds, plus Vitest for unit tests. Not the app bundler.
react + js
UI layer. Plain JavaScript with jsconfig.json path aliases — no TypeScript build step.
three.js
The actual 3D engine. Lives behind a thin lib/three/ layer of pure, React-free helpers.
@react-three/fiber
React renderer for three.js. Declarative scenes; the bridge between the DOM tree and the WebGL tree.
@react-three/drei
Helper components — loaders, controls, environments, performance utilities. Reach here before writing your own.
tailwind + zustand
Tailwind for DOM/HUD overlays; zustand for shared state that both the DOM and the canvas read from.
WHY THIS MATTERS FOR CLAUDE

The boundaries above are exactly the kind of thing Claude will guess wrong if you don't write them down. "Vite is not the app bundler" and "lib/three/ is React-free" are one-line rules that prevent whole categories of mistakes — and they belong in CLAUDE.md, covered in section 06.

PART A · FOUNDATIONS / 02

How Claude Code fits a 3D project.

3D web work has more invisible rules than typical CRUD apps: a single misplaced new THREE.Vector3() inside a render loop, an undisposed geometry, or an unthrottled useFrame can quietly tank your frame rate. Claude Code earns its keep by encoding those rules once and applying them every time. Four leverage points:

Leverage 01 · Memory
Pin the non-obvious rules
Perf constraints, the lib/three/ boundary, the disposal contract. Encoded in CLAUDE.md + path-scoped rules so they never silently regress.
Leverage 02 · Skills
Scaffold the repetitive parts
A new 3D route, a GLB import-and-wire, a shader material — multi-step boilerplate becomes a single invokable skill with templates.
Leverage 03 · Agents
Isolate the risky reviews
A perf auditor and a shader reviewer run in their own context windows, so a deep audit never pollutes your main working thread.
Leverage 04 · MCP
Reach the asset pipeline
Wire Claude to Blender for authoring/export and to the running dev server for live profiling — closing the Blender → glTF → R3F loop.

RULES vs SKILLS vs COMMANDS

All three become markdown the model reads, but loading differs. Rules are always-on when their path glob matches. Skills are progressively disclosed — only name + description sit in context until Claude decides to invoke one. Commands are invoked explicitly with /name. Hooks aren't files of their own; they're configured inside settings.json.

PART C · CONFIGURATION / 06

CLAUDE.md & memory.

This file is loaded on every interaction, so every token competes for attention — keep it under roughly 500 tokens. It should carry the things Claude can't infer from the code: stack boundaries, the disposal contract, and the handful of perf rules that matter most. Defer the long lists to path-scoped rules (§07).

# orbital-atlas — multi-page 3D web app

## Stack
Bun (pm + runtime) · Next.js App Router · React + plain JS (no TS).
three.js via @react-three/fiber + drei. Tailwind for DOM/HUD. zustand for shared state.
Vite is ONLY the component sandbox + Vitest — never the app bundler.

## Architecture boundaries
- `components/` = declarative React/R3F. `lib/three/` = pure three.js, NO react imports.
- The `` lives in `components/canvas/CanvasRoot.jsx`, lazy-loaded behind Suspense.
- DOM and canvas share state only through `lib/store.js` (zustand).

## Hard performance rules (non-negotiable)
- Never allocate (`new THREE.*`, arrays, objects) inside `useFrame` or render.
- Reuse geometries/materials from `lib/three/materials.js`; dispose on unmount.
- Default `frameloop="demand"`; call `invalidate()` on change. No always-on loops.
- Many copies of one mesh → `InstancedMesh`, never a `.map()` of meshes.

## Conventions
- Import drei helpers before hand-rolling (Loader, Environment, useGLTF, Instances).
- GLB assets are draco+ktx2 compressed via the gltf-pipeline skill — never commit raw exports.
- Run `bun run check` (lint + vitest) before declaring a task done.

# Gotcha: drei `useGLTF` caches by URL — preload with useGLTF.preload().
SPLIT YOURS FROM THE TEAM'S

Anything true only for you — your Neovim/LazyVim setup, your local model paths, your GPU quirks — goes in ~/.claude/CLAUDE.md (global) or CLAUDE.local.md (this project, gitignored), not in the shared file.

PART C · CONFIGURATION / 07

Path-scoped rules.

Rules are always-on, but only when their globs match the file Claude is touching. This is how you keep the heavy detail out of CLAUDE.md: a shader rule loads only in shaders/**; an R3F rule only when editing scene components. Here's the mapping for this project:

Rule fileGlobsCarries
js-style.md**/*.{js,jsx}Plain-JS conventions, JSDoc for shared utils, @/ import aliases, no default exports for components.
r3f-conventions.mdcomponents/three/**Declarative-only scene graph; use <Instances>; no imperative scene mutation; refs over state for transforms.
three-perf.mdlib/three/**, hooks/**Allocation-free hot paths, shared material/geometry registry, explicit .dispose(), object pooling.
shaders.mdshaders/**GLSL precision, uniform naming, documented varyings, how to register a shaderMaterial via drei.
next-app-router.mdapp/**Server vs client components, where 'use client' belongs, dynamic-import the canvas with ssr:false.
tailwind-ui.mdcomponents/ui/**HUD overlay patterns, pointer-events discipline over the canvas, design tokens, no inline styles.

A rule is just markdown with YAML frontmatter declaring its scope:

---
description: R3F scene component conventions
globs: ["components/three/**", "components/canvas/**"]
---

# React Three Fiber — scene components

- Keep the scene graph declarative. Mutate transforms through a ref in
  `useFrame`, not via React state (state in the loop = re-render storms).
- More than ~20 copies of a mesh → `<Instances>` / `InstancedMesh`.
- Pull materials from `lib/three/materials.js`; never inline `new MeshStandardMaterial`.
- Wrap async children (`useGLTF`, `useTexture`) in `<Suspense>` with a Loader fallback.
PART C · CONFIGURATION / 08

Settings, hooks & MCP.

Three concerns share one home or sit beside it: settings.json holds permissions, model defaults, and hooks; .mcp.json declares external tools. Hooks are the highest-leverage piece for a 3D project — they let you run your real checks automatically after Claude edits a file.

// .claude/settings.json
{
  "model": "claude-opus-4-8",
  "permissions": {
    "allow": [
      "Bash(bun run *)",
      "Bash(bunx gltf-transform *)",
      "Edit", "Read"
    ],
    "ask": ["Bash(git push *)"]
  },
  "hooks": {
    "PostToolUse": [{
      "matcher": "Edit|Write",
      "hooks": [{ "type": "command",
        "command": "bun run lint --filter $CLAUDE_FILE_PATHS" }]
    }]
  }
}
// .mcp.json — team-shared external tools
{
  "mcpServers": {
    "blender": {
      // author + export assets; closes the Blender → glTF → R3F loop
      "command": "uvx",
      "args": ["blender-mcp"]
    },
    "filesystem": {
      // scope Claude to assets, not the whole disk
      "command": "bunx",
      "args": ["@modelcontextprotocol/server-filesystem", "./public/models"]
    },
    "chrome-devtools": {
      // profile the running dev server: FPS, draw calls, memory
      "command": "bunx",
      "args": ["chrome-devtools-mcp@latest"]
    }
  }
}
# What the PostToolUse hook buys you

SessionStart   → print perf budget + the disposal contract reminder
PostToolUse    → after every Edit/Write, lint the touched file
                 (catch a stray `new THREE.Vector3()` in a loop immediately)
Stop           → run `bun run check` (lint + vitest) before finishing

# Hooks turn your conventions into something the machine enforces,
# not something Claude has to remember. Define them once in settings.json.
PERSONALIZED — YOUR PIPELINE

The blender MCP server is the standout here: it lets Claude drive asset authoring and export, so a request like "decimate this mesh and re-export as draco GLB into public/models" flows straight through the gltf-pipeline skill (§09) and into the scene — no manual round-trips.

PART D · WORKFLOWS / 09

Skills for 3D.

A skill bundles a multi-step workflow with its templates and reference docs. Only the frontmatter name + description load by default; the body is read when Claude decides the skill applies. Two pull their weight in this project:

09.1new-scene-route

Scaffolds a new page under app/, wires a lazy <Canvas>, and registers a scene component — from a single ask like "add an explore page with an orbiting model."

---
name: new-scene-route
description: Scaffold a new multi-page 3D route — App Router page, lazy
  Canvas mount, and a starter R3F scene wired to the zustand store.
---

# New scene route

## 1. Confirm intent
Ask for the route segment, the GLB asset (if any), and whether it needs HUD overlays.

## 2. Scaffold from templates
Copy `templates/page.jsx.tmpl` → `app/<segment>/page.jsx` and
`templates/Scene.jsx.tmpl` → `components/three/<Name>Scene.jsx`.

## 3. Mount the canvas correctly
Import `CanvasRoot` with `next/dynamic` and `{ ssr: false }`; wrap the scene in Suspense.

## 4. Verify
Run `bun run check`. Confirm `frameloop="demand"` and that no material is inlined.

See `reference/r3f-canvas-patterns.md` for the canonical mount pattern.

09.2gltf-pipeline

Takes a raw export and produces a web-ready asset: Draco/meshopt geometry compression, KTX2 textures, and a generated typed accessor — then drops it into public/models. Ships an optimize.sh wrapping gltf-transform, and pairs naturally with the Blender MCP server for the authoring step.

PROGRESSIVE DISCLOSURE

Because only the description sits in context until invoked, you can keep many skills around cheaply. Write descriptions that say when to use the skill, not just what it does — that's the signal Claude matches against.

PART D · WORKFLOWS / 10

Subagents.

A subagent runs in its own context window with its own system prompt and a restricted tool list. Use them for deep, noisy tasks you don't want cluttering the main thread — and for tasks where a narrow toolset is a safety feature.

---
name: perf-auditor
description: Audits R3F/three.js code for frame-rate hazards. Invoke
  before merging scene changes or when FPS regresses.
tools: [Read, Grep, Bash]
---

You are a WebGL performance auditor. Scan only for runtime cost. Report, do not refactor.

Checklist
1. Allocations inside `useFrame` / render (`new THREE.*`, array/object literals).
2. `setState` driving per-frame transforms instead of refs.
3. Always-on `frameloop` where `"demand"` + `invalidate()` would do.
4. Repeated meshes that should be `InstancedMesh`.
5. Missing `.dispose()` on unmount; uncompressed GLB / textures.
6. `dpr` not clamped on high-DPI displays.

Output: a ranked table — file:line · severity · fix. Nothing else.

A shader-reviewer agent follows the same shape, scoped to GLSL correctness and precision. Pair either with the terse-review.md output-style so the report stays scannable.

WHY ISOLATE

A perf audit reads dozens of files and emits a long report. Running it as a subagent keeps all that out of your main context, so the conversation where you're actually building stays focused and cheap.

Where does this go?

You've got a new piece of guidance for Claude. Walk the tree until you hit a destination — click the answer that matches.

Will every interaction in this project need it?
Does it apply only inside a specific folder or file type (e.g. shaders/**)?
Is it a multi-step workflow with its own templates (e.g. scaffolding a scene)?
A one-shot prompt you want to fire on a slash key?
A specialist review that should run in its own isolated context?
Is it about permissions, hooks, env vars, or model defaults?
DESTINATION

Guardrail: if it's true for you but not the team, copy it into CLAUDE.local.md or .claude/settings.local.json — both gitignored.

PART E · PERFORMANCE / 12

R3F performance guardrails.

These are the rules worth encoding into memory and enforcing through agents and hooks. None are exotic — they're just easy to forget, and expensive when forgotten. This table is the source material for three-perf.md and the perf-auditor agent.

RuleWhyEnforced where
No allocs in useFramePer-frame new THREE.* / literals spike GC and stutter the frame.three-perf · agent
frameloop="demand"Render only on change via invalidate(). Idle scenes cost ~0%.CLAUDE.md · r3f
Refs over stateDriving transforms with setState triggers React re-renders every frame.r3f-conventions
InstancedMeshOne draw call for N copies instead of N draw calls.r3f · agent
Shared materials/geoReuse from a registry; identical materials should be one object.three-perf
Dispose on unmountGeometries, materials, and textures leak GPU memory if not disposed.three-perf · hook
Draco + KTX2Compressed geometry and GPU textures cut payload and VRAM dramatically.gltf-pipeline
Clamp dprdpr={[1, 2]} — uncapped retina rendering quadruples fragment work.r3f-conventions
Lazy Canvas + SuspenseDynamic-import the canvas (ssr:false); keep WebGL off the critical path.next-app-router
Respect reduced-motionGate auto-rotation/effects behind useReducedMotion.tailwind-ui · hooks
