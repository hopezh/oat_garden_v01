Recipe · yt-dlp 2026.06.09 · project-scoped via uv

Archive a whole channel,
at full resolution,
without getting blocked.

Two commands pull a YouTube channel's long-form videos and Shorts into separate folders — best available quality, metadata alongside, request spacing tuned so a 200-item run finishes instead of collecting 403s halfway through.

TL;DR

Survey, then download — twice, sequentially

List the channel with --flat-playlist before committing. Then run one yt-dlp invocation per tab (/videos, /shorts), each with its own output folder and its own --download-archive. Leave the format selector alone — the default already resolves to the highest quality.

  • →No -f flag. The default bv*+ba/b is max resolution; -f best would silently cap you near 720p.[2]
  • →Three spacing knobs, not one: metadata requests, downloads, and subtitle fetches each burst separately.
  • →--download-archive makes the run resumable — re-running the identical command fetches only what is new.[5]
  • →%(upload_date)s leads the filename, or the folder sorts alphabetically by title, which is useless for a channel.
  • →Run the two commands one after the other, never in parallel — concurrency defeats the spacing.

01 · Prerequisites

three pieces · one project-scoped

yt-dlp

Lives inside the project's virtualenv, not on PATH. Every command therefore goes through uv run, which resolves the venv without activation.[6]

project-scoped

Deno

YouTube wraps player logic in JavaScript that must be executed to see the full format list and solve the n-parameter challenge. Without a JS runtime, some videos fail with HTTP 403.[4]

system-wide

FFmpeg

The highest-resolution renditions ship as separate video and audio streams. FFmpeg is what merges them back into one file — without it, yt-dlp falls back to lower pre-muxed formats.[7]

system-wide

Installing the two system-wide pieces

Only Deno and FFmpeg are installed globally; yt-dlp deliberately is not. Skip this entirely if deno --version and ffmpeg -version already answer.

# PowerShell — winget
winget install DenoLand.Deno
winget install Gyan.FFmpeg

deno --version; ffmpeg -version
# Homebrew
brew install deno
brew install ffmpeg

deno --version && ffmpeg -version
# Deno installer + your distro's package manager
curl -fsSL https://deno.land/install.sh | sh
sudo apt install ffmpeg   # or dnf / pacman

deno --version && ffmpeg -version

02 · Look before you leap

step one · costs nothing

--flat-playlist enumerates a channel without touching a single media stream: it resolves the tab to a list of IDs and stops. Run it first — it tells you the real size of the job and confirms the URL resolves before you commit to hours of downloading.

uv run yt-dlp --flat-playlist --print "%(id)s  %(title)s" "https://www.youtube.com/@MarathonTheGame/videos"

03 · The download commands

step two · run sequentially

04 · One video, not a channel

variant · a single URL

The same tool grabs a single video — point it at a watch?v=<id> URL and drop the two channel-scale flags. There is no playlist to enumerate, so --download-archive and the --sleep-* spacing earn nothing: one video is one burst. Keep the --write-* sidecars; they behave exactly as they do on the channel run.

uv run yt-dlp `
  -o "downloads/youtube-single/%(upload_date)s - %(title)s [%(id)s].%(ext)s" `
  --write-info-json --write-thumbnail --write-description `
  --write-subs --write-auto-subs --sub-langs "en.*" `
  "https://www.youtube.com/watch?v=<id>"
uv run yt-dlp \
  -o 'downloads/youtube-single/%(upload_date)s - %(title)s [%(id)s].%(ext)s' \
  --write-info-json --write-thumbnail --write-description \
  --write-subs --write-auto-subs --sub-langs 'en.*' \
  'https://www.youtube.com/watch?v=<id>'
uv run yt-dlp \
  -o 'downloads/youtube-single/%(upload_date)s - %(title)s [%(id)s].%(ext)s' \
  --write-info-json --write-thumbnail --write-description \
  --write-subs --write-auto-subs --sub-langs 'en.*' \
  'https://www.youtube.com/watch?v=<id>'

Transcripts come in whatever language the video has

--sub-langs is a filter, not a request: it writes only tracks that already exist. "en.*" against a video with no English captions matches nothing and writes no .vtt — silently, with no error. A missing subtitle file usually means the filter missed, not that a fetch failed. Confirm what a video actually carries before assuming:

# list every caption track without downloading anything
uv run yt-dlp --list-subs "https://www.youtube.com/watch?v=<id>"

Then aim --sub-langs at a track that exists. A Traditional-Chinese talk, for instance, may carry only a human zh-TW track and no auto-captions at all — so --write-auto-subs adds nothing, and only the explicit language pulls the transcript:

# transcript only, in the language the video actually has
uv run yt-dlp --skip-download --write-subs --sub-langs "zh-TW" "https://www.youtube.com/watch?v=<id>"
--sub-langs "en.*" Every English variant. The .* glob catches en, en-US, en-GB and yt-dlp's en-orig. A bare "en" misses the regional tags.
--sub-langs "zh-TW" · "zh.*" One language, or a whole family. Name the exact code for a single track, or glob the family (zh.* → zh-TW, zh-Hans, zh-HK) when you are unsure which regional variant the uploader used.
--sub-langs "all" Whatever exists, regardless of language. The safe choice for a mixed-language channel where no single code fits every video — at the cost of many tracks per video.
--write-subs vs --write-auto-subs Human-authored vs machine-generated. A video may carry one, both, or neither. Keep both for a complete archive; drop --write-auto-subs when only real captions matter. Neither invents a track YouTube does not serve.
--convert-subs srt Reshape after download. Captions arrive as .vtt; add this to convert them to .srt, .ass or .lrc for players that expect a different format.[1]

05 · Why each flag is there

five concerns · one command

Resolution — by omission

There is no -f flag in the command, on purpose. yt-dlp's default format selector is bv*+ba/b: take the best video-only stream, take the best audio-only stream, merge them, and fall back to a pre-muxed stream only if that is impossible.[2] Adding -f best is the single most common way people accidentally cap themselves at 720p — it restricts selection to streams that already contain both tracks, and YouTube stops publishing those above 720p.

Request spacing — three knobs, three different bursts

Throttling and 403s on long channel runs are driven by request rate, not by bytes transferred. Three separate phases each burst independently, so a single sleep flag does not cover them.

Metadata calls

--sleep-requests 1.5 pauses between API calls during enumeration and per-video info extraction. On a 169-item tab this phase fires hundreds of requests before a single byte of video moves — it is the highest-risk phase.

1.5 s between requests

Between downloads

--min-sleep-interval 5 with --max-sleep-interval 15 waits a randomized 5–15 s between videos. Randomized rather than fixed, so the request pattern does not look mechanically scripted.

5–15 s, randomized

Subtitle fetches

--sleep-subtitles 3 covers a phase people forget: subtitles are fetched as their own requests, once per language per video. Without it they burst immediately after each download completes.

3 s per subtitle

Metadata alongside the media

The --write-* family produces sidecar files next to each video rather than embedding data inside the container. This matches the sidecar convention the ArtStation half of this project already uses,[3] and it keeps the metadata greppable without re-muxing.

Sidecar files (used here)

--write-info-json, --write-thumbnail, --write-description, --write-subs, --write-auto-subs. Produces .info.json, .webp, .description and .en.vtt beside every media file.

readable without touching the video

Embedded alternative

Swap in --embed-metadata --embed-thumbnail --embed-subs to fold everything inside the mkv/mp4 instead. One self-contained file per video, at the cost of a post-processing pass and losing easy text search.

one file per video

Archive and naming — the two channel-specific flags

--download-archive <path> Makes the run resumable. Every completed video ID is appended to the file; on a re-run those IDs are skipped before any network request is made. This is what makes it safe to interrupt a 219-item job with Ctrl-C and simply re-issue the same command later. Failed videos are deliberately not recorded, so a re-run retries exactly them. The same pattern is used by this project's recover_embeds.py.[5]
-o "%(upload_date)s - %(title)s [%(id)s].%(ext)s" Puts chronology in the filename. Without the date prefix the folder sorts alphabetically by title — meaningless for a channel, where publication order is the structure. The trailing [%(id)s] guarantees uniqueness when two uploads share a title and gives you the ID back for any follow-up fetch.

Resilience on a long run

--ignore-errors One bad video must not end the run. Across a couple hundred items you will hit a region-locked, private or removed upload. Without this flag the whole job aborts there; with it the failure is logged and skipped — and since it never enters the archive, the next run retries it.
--retries 10 --fragment-retries 10 Transient failures are the norm, not the exception, on multi-hour runs. Fragmented DASH downloads in particular drop individual fragments that succeed on a second attempt.
--retry-sleep fragment:exp=2:60 Backs off exponentially — 2 s, 4 s, 8 s … capped at 60 s — instead of retrying immediately. Retrying a rate-limited request without backoff is what converts a soft throttle into a hard block.

06 · In practice

pitfalls · timing
  • →Run the two commands sequentially, never in parallel. Two concurrent yt-dlp processes against one channel double the request rate and defeat every sleep flag above. Sequential is the entire point.
  • →Use the explicit tab URL. The bare youtube.com/@MarathonTheGame root pulls every tab — videos, shorts, live, releases — which is far more than intended and mixes the two target folders together.
  • →--write-auto-subs roughly doubles subtitle requests. It pulls machine-generated captions wherever human ones are absent. Drop it if only real subtitles matter; keep it for a complete archive.
  • →Emoji and pipes in titles are handled automatically. Shorts titles routinely contain |, ? and emoji; yt-dlp sanitizes characters illegal on the host filesystem. Add --restrict-filenames only if the archive will later move to a stricter filesystem.
  • →Narrow the job when testing. --playlist-items 1:5 verifies the whole pipeline — naming, sidecars, merge — in a couple of minutes before committing to the full run.
  • →Rewrite embed URLs before feeding them in. A youtube-nocookie.com/embed/<id>?list=… link is mis-routed to the generic extractor and fails with Unsupported URL; the plain watch?v=<id> form works.[5]
