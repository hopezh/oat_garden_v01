Workflow Guide

ArtStation Batch Downloader

A project-scoped uv + gallery-dl setup to archive images and videos from ArtStation — one config, three URL shapes, fully resumable.

⚡ TL;DR

Spin up an isolated uv project, add gallery-dl + yt-dlp into it, drop in a gallery-dl.conf, then run uv run gallery-dl -c gallery-dl.conf <url> for a single post, a whole artist, or a tag collection (via search). Always dry-run with -s, then a capped --range 1-50 batch, then the full run. Everything lands in downloads/artstation/<artist>/ beside a .json metadata sidecar. Posts with embedded YouTube videos additionally need a JS runtime (Deno) plus the yt-dlp EJS solver — see §2 and §4. Hit a warning mid-run? The troubleshooting table in §8 maps each message to its fix. Want everything in one flat folder under its original ArtStation filename instead of the per-artist tree? Run merge_downloads.py afterwards — §10.

01Initialise the project with uv

uv init scaffolds a project folder with a pyproject.toml. Every dependency you add from here is recorded there and installed into a project-local .venv/ — nothing touches your global Python.[4]

uv init artstation-dl
cd artstation-dl

02Install gallery-dl & yt-dlp — project scope only

uv add installs both packages into ./.venv and records them as dependencies. The executables live inside the venv and don't exist on your PATH outside this folder — exactly the isolation we want.[1]

uv add gallery-dl "yt-dlp[default]"
Cloning this repo from GitHub? Skip the uv add above — the dependencies are already pinned in pyproject.toml / uv.lock. Just run uv sync to recreate the exact environment in ./.venv.

You run tools through uv run, which puts the project venv on the path for just that one invocation:

uv run gallery-dl --version

yt-dlp is paired in because gallery-dl hands embedded video players (YouTube / Vimeo) off to it.[3] The [default] extra covers yt-dlp's core dependencies but not curl_cffi, which yt-dlp needs to impersonate a browser for Vimeo embeds — without it, Vimeo downloads warn (no impersonate target is available) and often fail. Add it only if you hit that (see §8). Keep yt-dlp current as a hedge against ArtStation video changes: uv lock --upgrade-package yt-dlp.

Where the installed executable actually lands differs by OS:

./.venv/bin/gallery-dl
./.venv/bin/gallery-dl
.\.venv\Scripts\gallery-dl.exe
Project-scoped, not global. uv add + uv run keeps everything in the project. That's deliberately different from uv tool install / uvx, which expose a command globally on your PATH.[4]
Figure 1 — The three-command setup pipeline, all contained in the project venv.

A JavaScript runtime (Deno) — only for YouTube / Vimeo embeds

When a post embeds a YouTube / Vimeo player, external: true (see §4) hands it to yt-dlp. Modern YouTube wraps its player logic in JavaScript that yt-dlp must execute to (a) see the full list of formats and (b) solve the n-parameter challenge that unlocks the media URLs. With no JS runtime available, yt-dlp prints a deprecation warning and — for some videos — fails the download outright with HTTP Error 403: Forbidden.[3]

yt-dlp looks for Deno by default, so install it once — system-wide, not inside the venv:

brew install deno
curl -fsSL https://deno.land/install.sh | sh
winget install DenoLand.Deno

Open a new terminal (so PATH refreshes), then confirm with deno --version. yt-dlp picks it up automatically — but Deno alone isn't always enough: pair it with the EJS solver wired into the config in §4. Still seeing No supported JavaScript runtime after installing? The terminal was likely opened before the install — see the PATH check in §8.

System-wide, by necessity. Unlike gallery-dl / yt-dlp, Deno can't be project-scoped — yt-dlp needs a real JS runtime on your PATH, not a Python package. Skip this entirely if you never grab posts with embedded videos.

03The three download scenarios

All three use the same command; only the URL changes. Each URL is matched by a different gallery-dl ArtStation subcategory.[1]

ScenarioExample URLSubcategory
Single post/artwork/y4wVnnimage
Whole artist gallery/dgoryainovuser
A collection (via search)/search?tags=TheArtofMarathonsearch
Figure 2 — Each URL shape routes through its own extractor but converges into per-artist folders.

The commands

# Single post
uv run gallery-dl -c gallery-dl.conf "https://www.artstation.com/artwork/y4wVnn"

# Whole artist gallery
uv run gallery-dl -c gallery-dl.conf "https://www.artstation.com/dgoryainov"

# A collection, via search
uv run gallery-dl -c gallery-dl.conf "https://www.artstation.com/search?tags=TheArtofMarathon"
Use the search URL, not the channel URL. The curated …/channels/tag/TheArtofMarathon page matches no gallery-dl extractor (verified on gallery-dl 1.32.3) and will error out. The …/search?tags=… form is what the search subcategory handles. Results may differ slightly from the visual channel page, so preview with -s first.[1]

04The gallery-dl.conf and its settings

gallery-dl does not auto-load a config from the current directory — its default search paths are /etc/gallery-dl.conf, ~/.config/gallery-dl/config.json, and ~/.gallery-dl.conf.[2] Pointing at the file explicitly with -c gallery-dl.conf is what keeps the config project-scoped: it travels with the project and never pollutes anything global.

The file

{
  "extractor": {
    "base-directory": "./downloads",
    "archive": "./downloads/.archive.sqlite",
    "artstation": {
      "external": true,
      "videos": true,
      "mviews": true,
      "sleep-request": 1.5,
      "postprocessors": [
        { "name": "metadata", "mode": "json" }
      ],
      "image":  { "sleep-request": 1.0 },
      "user":   { "sleep-request": 1.5 },
      "search": {
        "sleep-request": 2.5,
        "directory": ["{category}", "{user[username]}"]
      }
    }
  },
  "downloader": {
    "ytdl": {
      "cmdline-args": ["--remote-components", "ejs:github"]
    }
  }
}
Strict JSON only — gallery-dl config files reject // and /* */ comments (verified). Keep the file comment-free.

What each key does

KeyEffect
base-directoryRoot for all downloads (./downloads).
archiveSQLite ledger of finished files → runs become resumable & idempotent; done assets are skipped on re-runs.
externalFollow embedded video players and delegate them to yt-dlp.
videosDownload native ArtStation video clips (on by default; set explicitly).
mviewsDownload Marmoset .mview 3D-viewer files when present.
sleep-requestBase politeness delay (seconds) between HTTP requests.
postprocessorsmetadata / json → writes a .json sidecar beside every file.
per-subcategory
sleep-request		The channel-vs-artist timing, baked in: image 1.0s · user 1.5s · search 2.5s. Subcategory blocks override the base; shared keys like external are inherited.
search.directoryOverrides the default Searches/<query> folder so the collection still sorts per-artist via each post's author {user[username]}.
downloader.ytdl
cmdline-args		Flags passed straight to yt-dlp. --remote-components ejs:github fetches the EJS challenge-solver script and runs it (via the Deno runtime from §2) to solve YouTube's n-parameter challenge — without it some embedded videos fail with HTTP Error 403: Forbidden. Downloads once, then cached; harmless when not needed.[7]

05Running it: dry → capped → full

A safe three-step ramp, shown for the largest (search) target.

Figure 3 — The dry → capped → full ramp; the archive makes each stage build on the last.

Step 1 — Dry run (downloads nothing)

-s (simulate) walks the whole result set and prints every path it would write — zero bandwidth, zero disk. Use it to gauge scale and confirm folder names.

uv run gallery-dl -c gallery-dl.conf -s "https://www.artstation.com/search?tags=TheArtofMarathon"

For a quick peek instead of the whole set, combine with a range:

uv run gallery-dl -c gallery-dl.conf -s --range 1-20 "https://www.artstation.com/search?tags=TheArtofMarathon"

Step 2 — Capped real download (first 50)

Downloads only items 1–50 so you can verify files, resolution, and sidecars. These get recorded in the archive, so they won't be fetched again.

uv run gallery-dl -c gallery-dl.conf --range 1-50 "https://www.artstation.com/search?tags=TheArtofMarathon"

Step 3 — Full run (drop the range)

The archive makes this resumable: it skips the 50 already pulled and grabs the rest.

uv run gallery-dl -c gallery-dl.conf "https://www.artstation.com/search?tags=TheArtofMarathon"

Cancelling safely

Press Ctrl+C (on macOS too — not Cmd+C, which is copy). A dry run writes nothing, so cancelling costs nothing. Real downloads use a temporary .part file and only commit to the archive on completion, so an interrupt leaves at most one incomplete .part and an unrecorded entry — both picked back up by re-running the same command. A second Ctrl+C forces it down if the first doesn't catch.

06The downloads folder & JSON sidecars

With the config above, the layout is:

artstation-dl/ ├── gallery-dl.conf ├── pyproject.toml ├── .venv/ └── downloads/ ├── .archive.sqlite ← resume ledger └── artstation/ ├── dgoryainov/ │ ├── artstation_<id>_<assetid>_<title>.jpg │ ├── artstation_<id>_<assetid>_<title>.jpg.json ← sidecar │ └── … └── <another-artist>/ └── …

Filenames follow gallery-dl's default {category}_{id}_{asset[id]}_{title}.{extension}, so a multi-asset post stays grouped and ordered. All three scenarios converge into downloads/artstation/<artist>/ — per-artist folders, even for the search collection.

The JSON sidecar

One .json file accompanies every media file (from the metadata postprocessor). It stores the full project + asset metadata: title, description, posted date, author, tags, and — most usefully — the asset's true width / height. That lets you confirm you actually received full resolution rather than trusting it blindly.

Figure 4 — Each asset yields a media file plus a JSON sidecar carrying the true dimensions and credits.

A note on resolution

gallery-dl's ArtStation extractor automatically requests the largest variant, building the /8k/ (original) URL and falling back through /4k/ → /large/ → /medium/ → /small/ if a tier 404s.[5][6] The real ceiling is whatever the artist uploaded; the sidecar dimensions are your receipt.

Figure 5 — The extractor aims highest first; bar length is illustrative of relative pixel size, not exact.

07Downloading from a list of URLs

gallery-dl has a built-in input-file feature (-i / --input-file), so you needn't invoke it once per URL.[1] Two approaches:

Option A — URLs on the command line

Positional URLs are processed in order:

uv run gallery-dl -c gallery-dl.conf \
  "https://www.artstation.com/artwork/rlbxmm" \
  "https://www.artstation.com/artwork/y4wVnn"

Option B — a urls.txt file (recommended)

One URL per line. Lines starting with # are comments and blank lines are ignored, so you can annotate and group freely.

# Marathon single posts
https://www.artstation.com/artwork/rlbxmm
https://www.artstation.com/artwork/y4wVnn

https://www.artstation.com/artwork/abcdEf
uv run gallery-dl -c gallery-dl.conf -i urls.txt

-i can be repeated (-i posts.txt -i artists.txt) and accepts - for stdin — handy for piping straight from your clipboard:

pbpaste | uv run gallery-dl -c gallery-dl.conf -i -
xclip -selection clipboard -o | uv run gallery-dl -c gallery-dl.conf -i -
Get-Clipboard | uv run gallery-dl -c gallery-dl.conf -i -

Self-updating variants

FlagBehaviour
-i FILERead URLs; file left untouched (rely on the archive for dedup).
-I FILEComments out each line once its URL finishes.
-x FILEDeletes each line after it completes.
-e FILEAppends URLs that errored to FILE — a ready-made retry list.
Figure 6 — One input file fans out to many posts; the archive keeps re-runs idempotent.
Pairs with the archive. Re-running the same -i urls.txt skips everything already downloaded, so you can keep appending URLs and re-run. These single-post URLs run through the image subcategory (1.0 s spacing).

08Troubleshooting embedded-video warnings & errors

Everything here concerns external videos embedded in posts (YouTube / Vimeo), which external: true (§4) hands to yt-dlp. None of it affects your ArtStation images or native ArtStation videos — those download regardless. And because the archive makes runs idempotent, the fix for any of these is the same: apply it, then re-run the exact same command — finished files are skipped and only the failed videos are retried.

Log line you sawCauseFix
No supported JavaScript runtime could be found · n challenge solving failedDeno isn't visible on the PATH of the shell you launched the download fromInstall Deno (§2), then make sure it's actually on PATH — see below.
[vimeo] attempting impersonation, but no impersonate target is available (often with Failed to parse XML)yt-dlp needs the curl_cffi library to impersonate a browser for Vimeouv add "yt-dlp[default,curl-cffi]" — the [curl-cffi] extra pulls in curl_cffi (the [default] extra does not).
Unsupported URL · Falling back on generic information extractor on a youtube-nocookie.com/embed/<id>?list=… linkA YouTube embed carrying a ?list= playlist param: yt-dlp (2026.06.x) mis-routes the embed+playlist URL to its generic extractor instead of YouTube. The video itself is fine.Recoverable — run recover_embeds.py against your run log (see §9) to re-fetch each one by its watch?v= URL.
Unsupported URL · Falling back on generic information extractor on any other embed hostexternal: true forwards every embedded link, including ones yt-dlp genuinely has no extractor forHarmless noise. Ignore it, or set "external": false to stop following embeds entirely.
[youtube] This video is not available · [vimeo] HTTP Error 401: UnauthorizedSource-side: the video was deleted, made private, region-locked, or embed-restrictedNot fixable — the content is gone or access-restricted on the host.

Make sure Deno is actually on PATH

The most common gotcha: you install Deno, but the terminal you launch the download from was opened before the install, so it still holds the old PATH and yt-dlp can't see Deno. The No supported JavaScript runtime warning then keeps appearing even though winget (or brew) reports Deno as installed.

  • Cleanest fix: open a new terminal, confirm deno --version, then re-run the same command.
  • Without opening a new terminal (Windows PowerShell):
$env:Path = [Environment]::GetEnvironmentVariable("Path","Machine") + ";" + [Environment]::GetEnvironmentVariable("Path","User")
deno --version
It's all embedded-video only. These warnings come from off-ArtStation players, never from ArtStation's own art or video. The archive means re-running after a fix costs almost nothing — already-downloaded files are skipped.

09Recovering missing YouTube embeds

One Unsupported URL case from §8 is not harmless noise. Some ArtStation posts embed YouTube as youtube-nocookie.com/embed/<id>?list=<playlist>. yt-dlp (2026.06.x) mis-routes that embed+playlist form to its generic extractor and gives up with Unsupported URL, so those videos are silently missing from your run. The archive doesn't help here — nothing was downloaded, so there's nothing recorded to skip or retry on a re-run.

The video itself is fine: fetched as a plain watch?v=<id> URL it downloads normally. recover_embeds.py automates exactly that — it scans a run log for these failed embeds and re-fetches each one.

When to reach for it. After any run whose log shows Failed to download ytdl:…youtube…/embed/… lines. If your log has none, the script is a no-op and tells you so.

Capture the log, then run the script

The script reads a log file, so capture your run's output first (this also gives you a record of everything downloaded):

uv run gallery-dl -c gallery-dl.conf "<url>" 2>&1 | Tee-Object download_log.md

Then point the recovery script at that log:

uv run python recover_embeds.py download_log.md            # re-fetch the missing embeds
uv run python recover_embeds.py download_log.md --dry-run   # just list what it found

It re-downloads each video by watch?v= URL into ./downloads/youtube_embeds/ and keeps its own .ytdl-archive.txt there, so re-running only fetches what's still missing — the same idempotent behaviour as a normal gallery-dl run.

Why a separate folder. The log doesn't reliably map each embed back to the post (and artist subfolder) it came from, so recovered videos land together in youtube_embeds/ rather than scattered across the per-artist tree.

10Flattening the downloads into one folder

The per-artist layout from §6 is ideal for browsing by author, but the filenames in it are gallery-dl's own construction — artstation_<id>_<assetid>_<title>.jpg — not the name you'd get by right-clicking the image on ArtStation. merge_downloads.py copies the whole tree into a single flat folder, renaming each file back to that manual-download name, which it reads from the file's .json sidecar (the {filename}.{extension} pair).

It copies, never moves. Your original downloads/ tree is left completely untouched, so a bad run costs nothing but disk. Sidecars and .archive.sqlite are skipped — only media files are merged.

Preview, then run

uv run python merge_downloads.py ./downloads ./downloads_merged --dry-run   # preview
uv run python merge_downloads.py ./downloads ./downloads_merged             # do it

--dry-run prints every planned copy and the full summary without writing anything — the same dry → real ramp as §5.

Duplicates & name collisions

Flattening a tree means two files can land on the same name. The script decides by content, not by name — it compares SHA-256 digests, so it only ever collapses files that are genuinely the same bytes.

SituationWhat happens
Two files resolve to the same name and are byte-identical — the same artwork reposted, or a re-run over a target you already merged intoSkipped, counted under skipped (identical). Re-running against the same target is safe.
Two files resolve to the same name but have different contentBoth kept — the second is written as <name>_1.<ext>, _2, … and logged as WARNING: name collision.
A media file has no usable sidecar (missing, or malformed JSON)Falls back to the source file's own gallery-dl name and logs WARNING: no usable sidecar.

Every run ends with a summary, so a large merge stays auditable at a glance:

--- summary ---
media files seen:    1240
copied:              1187
skipped (identical): 51
collision suffixed:  2
no-sidecar warnings: 0
time elapsed:        63.41s
Same idempotent habit as the rest of the workflow. Because identical files are skipped, you can download more with gallery-dl and then re-run the exact same merge command — only the new files get copied across.
