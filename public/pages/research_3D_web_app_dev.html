Optimal Structure for a Multi-Page Interactive 3D Web Application

Research synthesis · compiled by the orchestrator from 8 sub-agent deliverables · 2026-05-31
Stack: Bun Next.js Vite Three.js R3F Drei Plotly.js Tailwind

1. Executive Summary

Building a multi-page, interactive, GPU-rich 3D web app comes down to one decision that cascades into everything else: use a single, persistent WebGL canvas that lives above the router and never unmounts HIGH. Every production reference for this stack — led by the official pmndrs/react-three-next starter — is built around it, because browsers cap live WebGL contexts at ~8–16 and tearing one down on every navigation is slow and visually broken (Drei View docs).

  1. Shell: Next.js App Router is the single shell. Vite is redundant for a multi-page app. HIGH
  2. Runtime: Bun for installs/scripts (10–15× faster); serve via Node/Vercel until Bun-as-runtime is validated. HIGH
  3. Canvas: One persistent <Canvas> in the root layout; pages portal 3D in via Drei <View> + gl.scissor. HIGH
  4. Organization: Split by renderer target (canvas/ vs dom/) first, then by feature. HIGH
  5. State: React/Zustand for discrete UI; refs + useFrame for per-frame. Never setState in the loop. HIGH
  6. Performance: Draco (~10× geometry), KTX2 (~10× VRAM), on-demand render, instancing, DPR clamp. HIGH
  7. Data viz: Plotly as DOM overlay panels in SVG mode — not inside the 3D scene. HIGH
The through-line: one canvas, one render loop, one WebGL context; DOM owns layout, the 3D layer tracks it; a thin store seam connects them.

3. Recommended Architecture

The four-layer model HIGH

LAYER 1 — DOM / UI Next.js pages, Tailwind, HUD, Plotly panels OWNS: layout, routing, 2D analytics ▲ tracks rects (View) │ events / state LAYER 2 — Scene ONE persistent <Canvas>, cameras, lights, <View> routing OWNS: the single WebGL context + render loop ▲ mounts features │ useFrame(dt) LAYER 3 — Tile / Feature self-contained 3D modules (ProductModel, DataScene…) OWNS: feature geometry graph + per-frame update ▲ uses │ assigns LAYER 4 — Shader/Material GLSL, custom materials, instanced attributes OWNS: GPU vertex/pixel computation ◄──── shared seam: Zustand store ────►

Separation-of-concerns rules

  • DOM never touches Three objects — it writes intent (selection, active scene, filters) to the store.
  • Scene layer owns the loop and context — exactly one <Canvas>, one frameloop policy.
  • Feature modules are leaf "tiles" exposing a subtree + optional useFrame updater mutating refs (never setState).
  • Shaders/materials reused, never recreated per frame.
  • Cross-layer communication = the store seam, not prop-drilling across the canvas.

Data flow: User action → DOM event → Zustand store → (a) UI re-renders via selector, (b) 3D features read store in useFrame via getState() and mutate refs. Discrete in, continuous out.

5. Routing & Navigation

One persistent canvas in the root layout; pages portal 3D into it via Drei <View> + gl.scissor. HIGH

// app/layout.tsx — canvas mounted once, never unmounts
export default function RootLayout({ children }) {
  return (
    <html lang="en"><body>
      {children}
      <Scene
        style={{ position:'fixed', inset:0, pointerEvents:'none' }}
        eventSource={typeof document!=='undefined' ? document.body : undefined}
        eventPrefix="client" />
    </body></html>
  )
}
// components/canvas/Scene.tsx
'use client'
export function Scene(props) {
  return (
    <Canvas {...props} frameloop="demand">
      <r3f.Out />
      <View.Port />
      <Preload all />
    </Canvas>
  )
}
// app/products/page.tsx — map a DOM region to a viewport
'use client'
export default function ProductsPage() {
  return (
    <main className="grid grid-cols-2 gap-8 p-8">
      <section>{/* Tailwind DOM copy/UI */}</section>
      <View className="h-[60vh] w-full">
        <ProductModel />
        <OrbitControls makeDefault />
        <ambientLight intensity={0.6} />
      </View>
    </main>
  )
}

Why: Views use gl.scissor to cut the viewport into segments tied to a tracking div — "the illusion of multiple canvases" on one context. Two portaling mechanisms: Drei <View> (align to a DOM rect) and tunnel-rat (mark any component as 3D); react-three-next uses both. The persistent canvas enables camera transitions across routes.

Sources: Drei View, react-three-next, react-three-scissor.

6. State Management

Two-bucket model. HIGH Discrete, user-driven → React/Zustand (re-render). Per-frame, continuous → refs + useFrame (no re-render).

"If the update needs to happen every frame, use useFrame with refs; if it happens in response to user action, use React state — the two should rarely cross."
Lives in store/ReactLives in refs (useFrame)
selected object, active scene, filters, modal stateinterpolated positions, camera smoothing, animation progress

Cardinal anti-pattern: setState inside useFrame — routes a 60 fps update through React's scheduler → render storm.

// Transient read: latest store value every frame, no re-render
useFrame((_, dt) => {
  const target = useStore.getState().target          // no subscription
  ref.current.position.lerp(v.set(...target), 1 - Math.pow(0.001, dt))
})

7. Performance Guide

Three layers — Load, Runtime, Bundle. HIGH

Load

  • Code-split all 3D behind dynamic(...,{ssr:false}).
  • Draco geometry — up to 10× smaller glTF, decodes in a Web Worker.
  • KTX2/Basis textures — ~10× less VRAM, stay GPU-compressed.
  • Run gltf-transform (dedupe/prune/weld + Draco + KTX2).
  • Preload + Suspense: useGLTF.preload(), Drei <Preload all />.
  • Right-size textures (2048→1024/512, esp. mobile).

Runtime

  • InstancedMesh → "hundreds of thousands of objects in a single draw call."
  • frameloop="demand" + invalidate() (Drei controls auto-call it).
  • Clamp DPR dpr={[1,2]} / Drei <AdaptiveDpr/>.
  • Adaptive quality via Drei <PerformanceMonitor/>; LOD via <Detailed/>.
  • Reuse materials/geometries; no new THREE.* inside useFrame; dispose on unmount.

Bundle

  • Tree-shake Three.js; import Drei members individually.
  • Lazy-load Plotly + partial bundle (plotly.js-basic-dist).
  • Split heavy scenes per route.
MetricTarget
Frame rate60 fps (16.6 ms/frame); 30 fps mobile floor
Draw callsminimize via instancing/merging
Texture VRAM↓ ~10× via KTX2
glTF size↓ up to 10× via Draco
Initial JSkeep 3D/Plotly out of first load

8. Data Visualization Integration

Plotly.js and R3F compete for WebGL contexts (cap ~8–16; Plotly gl traces leak contexts on data update). Exceeding the cap drops the oldest context — possibly your Three.js canvas. MED

Recommended architecture HIGH

  1. One Three.js context (the persistent canvas) — never spawn extra R3F canvases.
  2. Prefer Plotly SVG traces (scatter, bar, line) for ≲ few-thousand points — zero WebGL contexts.
  3. Cap simultaneous Plotly gl charts; Plotly.purge() on unmount; update via Plotly.react.
  4. Lazy-load + partial bundle (full Plotly ≈ 3MB+).
  5. Layout, don't embed — charts are DOM panels beside/over the canvas, never inside the 3D scene.
// components/dom/charts/Chart.tsx
'use client'
import dynamic from 'next/dynamic'
const Plot = dynamic(() => import('react-plotly.js'), { ssr: false })
export function Chart({ data, layout }) {
  return <Plot data={data} layout={{ autosize:true, ...layout }}
           useResizeHandler className="h-full w-full" />
}

Plotly 3D vs Three.js: Plotly gl3d for standard statistical 3D charts (axes/hover free; budget one context each); Three.js/R3F for bespoke high-object-count experiences; Plotly SVG for 2D analytics. Cross-filter through the shared Zustand store. Don't render the same data in two WebGL contexts.

Sources: Too many WebGL contexts, react-plotly.js #191, Plotly 3D.

9. Patterns & Anti-Patterns

✅ Patterns

  • One persistent canvas above the router — warm GPU resources across navigation.
  • canvas/ vs dom/ split — client-only WebGL rule becomes a lint-able boundary.
  • Drei <View> maps DOM rects to viewports — DOM owns layout, 3D tracks it.
  • Two-bucket state — Zustand/React for discrete, refs+useFrame for per-frame.
  • Store as the only cross-layer seam — no prop-drilling across the canvas.
  • Asset compression by default — Draco + KTX2 via gltf-transform, offline.
  • Bun for tooling, Node/Vercel for runtime; Plotly as DOM panels in SVG mode.

❌ Anti-Patterns

  • A <Canvas> per page — context churn, lost resources, ~8-context cap risk.
  • setState inside useFrame — render storm, dropped frames.
  • DOM components importing/mutating Three objects — breaks the layer boundary.
  • Running Vite and Next.js as co-shells — duplicated bundling/routing.
  • Plotly gl charts everywhere / inside the 3D scene — exhausts WebGL contexts.
  • SSR-ing Three.js or Plotly — crashes on window; always ssr:false.
  • Shipping raw/uncompressed assets; creating new THREE.* every frame.

10. Appendices

Open questions for the project owner

  1. Device floor (desktop-only vs mobile) — sets DPR/texture/poly budgets.
  2. Bun as production runtime — recommend Node/Vercel runtime initially.
  3. Plotly chart count & update frequency — sets the WebGL context budget.
